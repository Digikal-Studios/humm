# M1 Benchmark Baselines

Criterion suite added in Task 9 (`crates/humm-core/benches/export.rs`,
`crates/humm-media/benches/decode.rs`, `crates/humm-whisper/benches/e2e.rs`).
These are the **M1 baselines** — every later milestone diffs its criterion
runs against these numbers. Per `CLAUDE.md`, a regression on the
`e2e/decode_transcribe` path (the real decode+transcribe path a user
exercises) is a **blocking failure to fix, not a note to log**; the
`export` and `decode` benches are supporting baselines for their own
adapters/writers.

## Host

- Chip: Apple M4 (10 cores: 4 performance + 6 efficiency)
- RAM: 32 GiB (34 359 738 368 bytes)
- macOS: 26.5.2 (build 25F84)
- Rust profile: `[profile.release]` — `lto = "thin"`, `codegen-units = 1` (workspace root `Cargo.toml`, unmodified by this task)
- Model: whisper `tiny`, GGML, GPU (Metal) on
- Fixture: Buzz's `whisper-french.mp3` testdata (`HUMM_BUZZ_TESTDATA`)

## Results

| Bench | Median | 95% CI (criterion) |
|---|---|---|
| `export/write_srt/10000_segments` | 4.0989 ms | [4.0408 ms, 4.1566 ms] |
| `export/write_vtt/10000_segments` | 2.4914 ms | [2.3647 ms, 2.6269 ms] |
| `export/write_txt/10000_segments` | 185.79 µs | [175.46 µs, 197.43 µs] |
| `decode/ffmpeg_decode/whisper-french.mp3` | 65.413 ms | [48.376 ms, 79.803 ms] |
| **`e2e/decode_transcribe/whisper-french.mp3/tiny`** | **386.20 ms** | [373.67 ms, 392.09 ms] |

`export` benches build 10 000 synthetic segments once and reuse a `Vec<u8>`
buffer (`sample_size` = criterion default 100). `decode` and `e2e` use
`sample_size(10)`; `e2e` additionally sets `measurement_time(60s)` per the
task brief (in practice all 10 iterations completed well inside that
window, ~76s wall including the 3s warm-up).

`decode` and `e2e` show wider CIs / outliers than `export` — both shell out
to a real `ffmpeg` subprocess (and `e2e` additionally loads/runs a real
whisper model on the GPU), so they're more exposed to the host's transient
load than the pure-Rust `export` bench. This machine is the developer's
primary laptop, not a dedicated/isolated benchmark rig; treat the CI width
as real variance, not just measurement noise, when diffing future runs.

## Reproducing

```bash
CARGO_HOME="$(git rev-parse --show-toplevel)/.cargo-home" cargo bench --workspace
```

`decode` and `e2e` skip (print a line, register no measurements, exit 0)
when `ffmpeg`, the Buzz testdata, or — for `e2e` — a real cached `tiny`
model is unavailable; `export` always runs (no external prerequisites).

## Environment finding: sandboxed shells can crash the GPU path — not a code bug

While first running this suite, `e2e` reproducibly **segfaulted** inside
`WhisperEngine::load(&model_path, true)` (GPU on) — signal 11, `EXC_BAD_ACCESS`
at `far = 0x10`, deep in ggml's Metal allocator:

```
ggml_metal_buffer_is_shared
ggml_backend_metal_buffer_type_private_alloc_buffer
alloc_tensor_range
ggml_backend_alloc_ctx_tensors_from_buft{,_impl}
whisper_init_with_params_no_state
whisper_init_from_file_with_params_no_state
whisper_rs::whisper_ctx::WhisperInnerContext::new_with_params
humm_whisper::engine::WhisperEngine::load
```

Root-caused by bisection, in order tried:

1. **Not the criterion suite's code** — the same crash reproduces from
   `cargo test -p humm-whisper --test contract -- --ignored transcribes_french_mp3`
   (pre-existing debug-profile contract test, unmodified), so it isn't
   specific to the new bench harness.
2. **Not `[profile.release]`'s `lto = "thin"` / `codegen-units = 1`** —
   disabling LTO for a scratch `[profile.bench]` override did not stop the
   crash (tested, then reverted — not present in the final diff).
3. **Is GPU-specific** — the identical bench with `WhisperEngine::load(&model_path, false)`
   (CPU) completed cleanly.
4. **Is specific to this coding harness's sandboxed shell** — the exact
   same GPU=true command, run with the harness's Bash sandbox restrictions
   lifted (nothing else changed), completed cleanly and produced the
   `e2e` median recorded above. The host has full Metal 4 support and a
   normal Aqua/WindowServer session (`system_profiler SPDisplaysDataType`,
   `launchctl managername` both confirm this); the sandbox layer appears to
   block some resource (most likely a Mach/IOKit lookup) `MTLCreateSystemDefaultDevice`
   needs, and ggml's Metal backend doesn't guard against that init failing
   (null buffer type â†’ null deref instead of a clean error or CPU fallback).

**No humm code changed as a result** — this is an artifact of how this
particular agentic coding tool sandboxes subprocesses, not a bug in
`WhisperEngine`, whisper-rs, or ggml's normal (unsandboxed) operation.
Anyone reproducing these numbers from an ordinary terminal should not hit
it. Logged so future milestones (and CI, if it ever runs inside a similar
sandbox) know to disable subprocess sandboxing — or run outside it — for
any command that loads a GPU model, and don't mistake the segfault for a
regression to bisect in humm's own code.
