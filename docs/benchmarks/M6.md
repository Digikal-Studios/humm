# M6 Benchmark Comparison & Acceptance

Per `CLAUDE.md`'s regression rule and `docs/benchmarks/M5.md` §1.2's standing
lesson: **re-baseline against a same-day checkout of the previous milestone's
tip, never against recorded numbers.** All runs 2026-07-25, sandbox-lifted
(Metal), Apple M4 / 32 GiB / macOS 26.5.2, whisper `tiny`, Buzz
`whisper-french.mp3`, criterion 10-sample runs — the same configuration as
M1–M5.

## 1. Transcription-path regression guard (`e2e`)

### 1.1 Conditions, stated up front

This machine carried heavy, *external* concurrent load for the entire
benching window — a different project's solver + two `generator_soak`
processes at ~100 % CPU each (verified via `ps`), load averages 7–19 across
runs. That load is not humm's and could not be paused. Absolute numbers are
therefore ~2× M5-era figures and meaningless in isolation; the comparison
below is **paired and interleaved** so both checkouts face the same
contention, which is the only honest read this environment allows (the same
"primary laptop, not a benchmark rig" caveat every prior milestone recorded,
at its worst so far).

### 1.2 Interleaved same-day pairs

M5 = worktree at `e15392c` (M5 tip); M6 = this branch's tip. Ordering
alternated to cancel order/thermal effects:

| Pair | M5 (mean) | M6 (mean) | Order | Load avg |
|---|---|---|---|---|
| A | 377.96 ms | 444.01 ms | M5→M6 | 10→19 (rising) |
| B | 672.21 ms | 504.45 ms | M6→M5 | ~13 |
| C | 397.64 ms | 413.44 ms | M6→M5 | ~10–12 |

Criterion CIs overlap heavily throughout (pair B's M6 CI alone spans
380–637 ms). **The sign of the M5↔M6 delta flips between pairs** — M6 is
"slower" under a rising load tail (A), "faster" under steady load (B),
and equal-within-noise (C). Pooled means: M5 ≈ 483 ms, M6 ≈ 454 ms.

### 1.3 Code-innocence evidence

`git diff e15392c..HEAD` on the `e2e` bench's call path:
`crates/humm-whisper` — **zero changes**; `crates/humm-media/src/decode.rs`
— a 7-line `pub(crate)` accessor addition (no decode logic touched; the M6
encode work lives in the new `encode.rs`). The bench never touches the
queue/pipeline (it drives decode + engine directly), and the M6 pipeline
changes are gated on `options.llm` being `Some` (structurally zero-overhead
when disabled — reviewed in Task 9).

### 1.4 Verdict

**No transcription-path regression detected.** The paired deltas sign-flip
inside overlapping CIs under documented external load, and the bench's call
path has no M6 code on it. Gate: PASS. (If a quiet-machine window appears
before merge-tag time, a clean-room pair would tighten this — but the
combination of interleaved-pair noise-boundedness and call-path innocence
already satisfies the M5-established standard, which explicitly rejects
comparing against recorded historical numbers.)

## 3. New-surface performance notes (informative, no baseline exists)

- The OpenAI engine's per-request overhead is network-dominated by design;
  its local costs (PCM slice → ffmpeg mp3 encode) are one subprocess per
  ≤25 MiB chunk — no criterion bench added (network-bound path, would
  measure the mock).
- Live translation adds one worker thread + one HTTP round trip per batch
  (≤10 utterances); the windowed acceptance run (`docs/gui-manual/M6.md`
  §1.1) showed no visible impact on the live session (3/3 utterances
  transcribed + translated in the 30 s window with the small model).
- The first real-hardware capture contract runs recorded effective capture
  rates of 15 962–15 999 Hz vs the nominal 16 000 (≤0.24 % — resample-path
  health, F-060) and `stop()` latencies of 7–10 ms.
