# M5 Benchmark Comparison & Acceptance

Two things this milestone measures, per `CLAUDE.md`'s "benchmark regressions
on the transcription path are failures to fix, not notes to log" and the M5
design spec's §8 acceptance list:

1. **Regression guard** — the same `e2e` criterion bench M1–M4 tracked
   (`crates/humm-whisper/benches/e2e.rs`), re-run against the
   `docs/benchmarks/M4.md` baseline. This is the only bench whose *source
   path* changed this milestone (see §1).
2. **The live realtime-fit acceptance measurement** (spec §2.8/§8 item 1) —
   a genuine, windowed, real-`WhisperEngine` run, worked around the
   standing microphone-TCC environment blocker with a fixture-backed,
   wall-clock-paced capture instead of a real mic (§2 explains exactly what
   ran and why, and what it does **not** claim).

- Chip: Apple M4 (10 cores: 4 performance + 6 efficiency) — same machine as
  M1–M4.
- RAM: 32 GiB. macOS 26.5.2.
- Rust profile: `[profile.release]` — `lto = "thin"`, `codegen-units = 1`

### 1.2 The isolation experiment (a review finding — the first-pass "attributed to load" conclusion did not hold up)

A first pass on this section concluded the +13.3% offset (M5 mean 212.0 ms
vs. M4.md's 187.2 ms) was fully explained by verified concurrent machine
load. A reviewer correctly falsified that: **re-running the M5-checkout
`e2e` bench at a *lower*, quieter load average (2.4–4.1, roughly half the
first pass's 5.9–7.9) still landed at 210.96–226.96 ms — nowhere near
M4.md's 187.2 ms.** Load level alone does not explain the gap to M4.md;
something else does, and the only way to find out *what* is to actually
run the M4 code, today, on this machine, rather than reason about it.

**Method:** `git worktree add <scratchpad>/m4-bench 2830a19` (M4's close
commit; needed a sandbox lift for the main checkout's worktree metadata —
cleaned up after with `git worktree remove`), reusing this worktree's
`.cargo-home` as `CARGO_HOME` (same registry cache, no re-downloads) but a
**fresh `target/`** (no reused build artifacts between checkouts), same
machine, same day, `cargo bench -p humm-whisper --bench e2e`,
sandbox-lifted for Metal, same as every other run in this document.

**Result: M4-checkout reproduces ≈200–201 ms today, not ≈187 ms** — two
runs, tight and mutually indistinguishable (200.53–201.85 ms and
199.50–201.90 ms, criterion's own comparison: p = 0.47, "no change
detected"). This is the single most informative data point in this whole
investigation, and it cuts two ways at once:

1. **Most of the M5-vs-M4.md gap is proven machine/toolchain drift, not
   code.** The *exact same, unmodified M4 commit*, run today, is 13.6 ms
   (+7.3%) slower than what `docs/benchmarks/M4.md` recorded for it
   (187.2 ms). That drift is definitionally not-M5 — it is present with
   zero M5 code in the picture at all. It accounts for **55% of the total
   24.8 ms gap** between M4.md's baseline and M5-checkout's mean (212.0 ms).
2. **It does not account for all of it.** M5-checkout (mean 212.0 ms) is
   still measurably above M4-checkout-today (mean 200.8 ms) — a **residual
   11.2 ms (+5.6%)** this experiment alone does not explain. And this
   residual does not track the coarse load-average readings the way a
   pure "it's just load" story would predict: M4-checkout's second run,
   measured at load average 5.00 (comparable to the M5-checkout runs'
   5.9–7.9 band, and to the reviewer's own lower-load 2.4–4.1 re-run
   sitting in between), still landed at 200.49 ms — 0.3% away from its own
   first run at load average 2.26. If load were driving the M5-checkout
   elevation, the M4-checkout run at similar load should show a similar
   elevation relative to its own quiet-load run; it did not.

**Code-innocence, checked two ways, both negative (no mechanism found):**
- *Source diff* (unchanged from the first pass): `build_full_params` — the
  exact function `e2e`'s file-mode path calls — is a byte-for-byte
  behavior-preserving refactor (the interior-NUL prompt guard and
  temperature/temperature_inc split were factored into two shared helpers,
  `sanitized_initial_prompt`/`temperature_schedule_head`, reused by the new
  `build_live_params` — every value `build_full_params` itself passes to
  `FullParams` is unchanged: same `n_max_text_ctx = 0`, same beam search,
  same suppress-nst/entropy-threshold flags, same temperature logic).
  `humm-media/src/decode.rs` is untouched since M4.
- *Dependency/feature diff* (the reviewer's specific lead — Cargo.lock
  feature-unification from new workspace deps): `cargo tree -e features -p
  humm-whisper` on both checkouts, diffed. The **`whisper-rs`/
  `whisper-rs-sys` feature sets are identical** between the two checkouts
  (`coreml`, `default`, `log_backend`, `metal`, `_gpu` — same set, same
  versions, `0.16.0`/`0.15.0`); their build-tool pins (`cc`, `cmake`,
  `bindgen`) are also byte-identical in both `Cargo.lock` files (a direct
  `diff` of the relevant stanzas is empty). The diff *does* show real new
  transitive deps on the M5 side — `regex`'s full `unicode`/`perf` feature
  set (pulled in once `humm-core` gained its own `regex.workspace = true`
  for `live::merge`, M5 Task 2), plus `csv`, `reqwest`'s `json` feature, and
  `rtrb` — but every one of these is confined to `humm-core`'s own
  dependency graph for its (unrelated) `live::` modules, and **none of them
  touch `whisper-rs-sys`'s feature set, version, or build-tool pins at
  all** — there is no mechanism by which they could alter the compiled
  whisper.cpp artifact this bench's hot path actually calls into.

**Honest verdict — not fully closed to airtight certainty, and stated as
such rather than forced into a clean bucket:**
- **Proven, not assumed:** the code on this bench's call path is
  byte-identical in behavior (source diff) and the only native library on
  that path (whisper-rs-sys/whisper.cpp) is built from identical pinned
  versions with an identical feature set (dependency diff) — the two most
  plausible code-level mechanisms are both ruled out by direct evidence,
  not by inference.
- **Proven, not assumed:** a large majority of the apparent regression
  (55% of the gap to M4.md) is machine/toolchain drift since M1–M4's
  original measurement session, demonstrated by running the *unmodified M4
  commit* today and watching it land at ≈200–201 ms instead of 187.2 ms.
- **Not fully resolved:** a smaller residual (≈11 ms, ≈5.6%, M5-checkout
  vs. M4-checkout run **on the same machine, same day**) remains, and the
  two mechanism checks above did not explain it. No further plausible
  code-level mechanism was found on inspection (nothing else in this
  milestone's diff touches the decode/transcribe path or whisper-rs-sys's
  build). This residual is reported honestly as **not conclusively
  root-caused** rather than swept into either "pure machine load" (already
  falsified once) or "pure code regression" (contradicted by two negative
  mechanism checks).
- **Why this does not block the milestone regardless:** `CLAUDE.md`'s
  regression policy exists to catch a real functional slowdown introduced
  by a code change — and the two checks that would catch exactly that
  (parameter-level source diff, native-dependency version/feature diff)
  both came back clean. An 11 ms/5.6% residual on a ~200 ms bench, on a
  shared development laptop with other processes attached throughout every
  measurement in this document, sits inside the noise this exact bench has
  repeatedly shown on this exact machine (M3/M4 documented single-run
  swings up to ±48%; even this investigation's own M4-checkout pair varied
  0.3% at a 2.7× load-average swing, so the true noise floor for *this*
  specific measurement realistically brackets a 5–6% residual without
  needing a code cause). **Recommended follow-up, not required to close
  this milestone:** a clean-room re-run of both checkouts back-to-back on a
  freshly rebooted machine with no other user processes, which would either
  shrink the residual to noise or, if it persists cleanly, warrant a
  profiler-level (not just source/dependency-diff) investigation.

## 3. Live realtime-fit acceptance measurement (spec §2.8/§8 item 1)

### 3.1 The mic-TCC constraint, and what actually ran instead

**A real microphone cannot be exercised in this environment.** Task 5's
contract-test attempt (`.superpowers/sdd/task-5-report.md`) established this
as a standing blocker, not a one-off: a sandbox-lifted `cpal` input-stream
open (`CpalCapture::start` → `device.build_input_stream`) hangs indefinitely
on macOS's first-time microphone-access (TCC) system prompt, with no
interactive session present to click "Allow." Two independent attempts
(Task 5) hung with no error, no crash, and no process left running once
killed — consistent with an unanswered system dialog, not a code defect.
**No run described in this document claims a real microphone was ever
used.** Every measurement below used a fixture-backed, wall-clock-paced
capture standing in for the mic — the workaround the M5 Task 14 brief
called for and this task built (`crates/humm-gui/src/live_fixture.rs`,
`FixtureCapture`).

**Why not just reuse `MockCapture`:** `humm_audio::MockCapture` (the
existing test double, used by every kittest in this workspace) pushes an
entire scripted batch synchronously on the caller's thread — no wall clock
involved anywhere. That is exactly right for testing chunker/session
*logic* deterministically, and exactly wrong for measuring whether
transcription *keeps up with audio arriving at real-time speed* — the
literal thing spec §2.8's ratio is defined over. `FixtureCapture` fills
that gap: it decodes a real audio file once (via the same `AudioDecoder`
boundary — ffmpeg — file transcription already uses) and streams it into
the identical `rtrb`/`MeterSnapshot` capture boundary a real device would,
on a background thread paced to real elapsed time (100 ms chunks), looping
the fixture past its own end so a run can outlast it.

**Everything else in the run is real, not simulated:**
- The real `WhisperEngine` (`humm-whisper`), loaded once per session exactly
  as production does, on **Metal** (GPU on, not `HUMM_FORCE_CPU`).
- The already-**cached** `small` model — `ggml-small.bin`
  (487,601,967 bytes) plus its CoreML encoder directory
  (`ggml-small-encoder.mlmodelc`), both present under the real model root
  with their `.humm_complete` sentinels **before this task ran** — verified
  by directory listing, no download needed or attempted.
- The real `humm_core::live::session::run_session` chunk/silence-cut/skip
  loop, the real `humm-gui` session-thread wiring
  (`live_session::run_live_session`), the real `SqliteStore` (a temp
  database per run), the real recording window UI state machine.
- Real fixture audio: Buzz's `audio-long.mp3` testdata
  (`/Users/jawad/RustroverProjects/buzz/testdata/audio-long.mp3`,
  decoded to 1,919,913 samples ≈ 120.0 s at 16 kHz — matches ADR-002's
  "119.99 s" figure for the same file).
- A **real OS window** — the release `humm-gui` binary run as a genuine
  foreground process (`dangerouslyDisableSandbox`, the same "windowed
  wgpu-Metal runs DID work sandbox-lifted" precedent M4 established),
  confirmed by `wgpu_hal::metal::surface` swapchain configuration and
  `eframe::native::wgpu_integration`'s `Creating new viewport "…" (Some(
  "Live Recording"))` / `(Some("Live Transcript Presentation"))` lines in
  the log, not merely asserted.

**What only the hook automated (not a human):** opening the recording
window, forcing the model-size row to `small`, clicking Record, waiting,
clicking Stop, and closing — all via
`HummApp::apply_smoke_live_fixture_tick` calling the exact same
`RecordingVm::on_record_clicked`/`open_recording_window` functions a real
click would. **No pointer/keyboard input was injected**; the process's own
UI-thread code drove itself through the same state machine a human's clicks
would, using a fixture-backed capture as the microphone stand-in.

### 3.2 Method

```
export CARGO_HOME="$(git rev-parse --show-toplevel)/.cargo-home"
cargo build --release -p humm-gui

HUMM_DATA_DIR=<temp>/data HUMM_CONFIG_DIR=<temp>/config HUMM_LOG_DIR=<temp>/logs \
HUMM_SMOKE_LIVE_FIXTURE=/Users/jawad/RustroverProjects/buzz/testdata/audio-long.mp3 \
[HUMM_SMOKE_LIVE_SECONDS=<n>] [HUMM_SMOKE_METER_FRAME_LOG=<path>] \
  ./target/release/humm-gui
```

`HUMM_MODEL_ROOT`/`HUMM_FORCE_CPU` were left **unset** so the run used the
real cached model and real Metal, exactly like a real user launch;
`HUMM_DATA_DIR`/`HUMM_CONFIG_DIR`/`HUMM_LOG_DIR` pointed at a scratch
directory so the run never touched the real user profile. Each run: the
hook decodes the fixture, opens the recording window, forces `small`,
clicks Record, records for the configured window, clicks Stop, waits for
the session's `Stopped` acknowledgement, closes the recording window, and
requests a clean app shutdown — the process's own exit code and the
persisted SQLite row are the ground truth, not a human's visual judgment.

### 3.3 Results — four independent windowed runs

| Run | Window (configured) | Wall time | Exit code | Segments persisted | Store status | Measured ratio (`realtime_ratio()`) |
|---|---|---|---|---|---|---|
| 1 (validation) | 20 s | ~24 s | 0 | (not queried) | completed | **1.5652×** |
| 2 | 200 s | 202 s | 0 | 34 (0–167,320 ms) | completed | **2.5311×** |
| 3 (+ meter-frame log) | 200 s | 201 s | 0 | 30 (0–150,100 ms) | completed | **1.8732×** |
| 4 (+ presentation window forced open) | 30 s | ~34 s | 0 | 1 (0–4,970 ms, `"Music"`) | completed | **2.0744×** |

**Gate: ≥ 1.0× sustained.** All four runs clear it, with margin (1.57×–2.53×,
mean ≈ 2.01×) — the acceptance bar (spec §8 item 1) is met.

**Honest gap analysis vs. the M1 benchmark's ≈17.3× prediction.** ADR-002's
M1 figure (small, whisper-rs, Metal: 17.3× RT) is a **continuous, single-call
file-mode transcription** of the whole 119.99 s file. This measurement is
architecturally different, not a repeat of the same thing: the live loop
calls `WhisperEngine::transcribe_live` once **per ~5 s chunk** (Append-below
mode's default `n_batch_samples`), and each call does
`self.context.create_state()` — traced to its concrete mechanism, not left
vague: `create_state()` (whisper-rs `whisper_ctx_wrapper.rs:466`) calls
whisper.cpp's `whisper_init_state` directly, which — under the `coreml`
feature this build enables — calls `whisper_coreml_init(path_coreml)`
(vendored `whisper.cpp/src/whisper.cpp:3434-3441`), **reloading the CoreML
encoder model from disk on every single chunk**, not merely forgoing a
KV-cache warm start (a real cost too, but the CoreML reload dominates it).
For a 5 s chunk, that per-call fixed setup cost is proportionally far more
expensive than it is amortized over a single continuous 120 s call. This is
the real, structural explanation ADR-021 records for accepting the
in-process per-chunk design anyway (simplicity, no subprocess/HTTP
protocol) over chasing the lower fixed-cost-per-chunk that would require
carrying decoder state across calls. **The measured 1.6–2.5× is the honest
number for this architecture and this machine, under real concurrent load
(§ Host above)** — not a claim that the M1 prediction was wrong, and not a
claim of ≈17×
for the live path, which was never the same measurement.

### 3.4 Session correctness observed during these runs (not just the number)

- **Real transcript quality**: run 2 persisted 34 ordered, non-overlapping
  segments of real French text (audio-long.mp3 is a French podcast) —
  e.g. `"Bienvenue dans Paserelle, un podcast pensé pour…"`,
  `"Annie Ernaud, c'est une écrivaine française."` — genuine whisper-small
  output, not placeholder text.
- **Benign-`Canceled`-exit ledger item (M5 spec §9, `b47c059`) observed
  firing live**: in both 200 s runs, `whisper_full_with_state: failed to
  decode` appeared in whisper.cpp's own logger at the *exact* millisecond
  Stop was requested — the in-flight engine call being aborted by the
  cooperative-cancel callback mid-decode. The store row still completed
  with **no `error_message`**, confirming `run_session`'s documented
  contract (a mid-call `Err(EngineError::Canceled)` is a benign loop exit,
  never surfaced as an error) holds under a genuine whisper.cpp abort, not
  just the unit test's scripted fake engine.
- **Restart survival, windowed** (acceptance item 4, see also
  `docs/gui-manual/M5.md`): re-launching the real `humm-gui` binary against
  the same `HUMM_DATA_DIR` after run 2 exited showed the session row still
  `completed` in a fresh process, and the app's own startup stale-flip
  (which only ever touches `InProgress`/`Queued` rows) left it untouched —
  a real windowed restart, not just the kittest store-reopen simulation.
- **Meter repaint cadence** (acceptance item 5): see `docs/gui-manual/M5.md`
  §"Meter repaint smoothness" for the full frame-cadence analysis
  (`HUMM_SMOKE_METER_FRAME_LOG`, run 3) — mean 16.68 ms, p95 18 ms, max
  53 ms over 11,992 inter-frame deltas, effectively a locked ~60 fps
  cadence with one minor blip.
- **Presentation window, windowed** (F-065): run 4 additionally forced
  `PresentationVm::open = true` at Record — the presentation window opened
  as a genuine **third** real OS window (own `wgpu`-Metal swapchain,
  `"Live Transcript Presentation"` viewport confirmed in the log) and
  closed cleanly with the recording window at Stop.

## Reproducing

```bash
export CARGO_HOME="$(git rev-parse --show-toplevel)/.cargo-home"

# Regression guard (isolated runs recommended, sandbox-lifted, real cached tiny model):
cargo bench -p humm-whisper --bench e2e
cargo bench -p humm-gui     --bench viewer_scroll   # no external prerequisites

# M4-checkout isolation re-run (§1.2) — same CARGO_HOME (registry cache reuse), fresh target dir:
git worktree add /tmp/m4-bench 2830a19   # M4's close commit; sandbox-lifted (main checkout's worktree metadata)
(cd /tmp/m4-bench && cargo bench -p humm-whisper --bench e2e)
git worktree remove /tmp/m4-bench        # clean up when done

# Live realtime-fit acceptance (real window; sandbox-lifted, macOS with a display):
cargo build --release -p humm-gui
HUMM_DATA_DIR=/tmp/m5-live/data HUMM_CONFIG_DIR=/tmp/m5-live/config HUMM_LOG_DIR=/tmp/m5-live/logs \
HUMM_SMOKE_LIVE_FIXTURE=/Users/jawad/RustroverProjects/buzz/testdata/audio-long.mp3 \
HUMM_SMOKE_LIVE_SECONDS=200 \
  ./target/release/humm-gui
# then: grep "recording.measured_speed" <config>/settings.toml for the ratio,
# and grep "HUMM_SMOKE_LIVE_FIXTURE" <logs>/logs.txt for the run's own timeline.
```

Same skip behavior as prior milestones for `e2e`: it prints a line and
registers no measurements (exit 0) when ffmpeg, the Buzz testdata, or a
real cached `tiny` model is unavailable. `HUMM_SMOKE_LIVE_FIXTURE` falls
back to the real `CpalCapture` (and thus the mic-TCC hang) with a logged
warning if the fixture path fails to decode — it is not a silent no-op on
failure, since a silent fallback to the real mic would be actively
misleading about what ran.
