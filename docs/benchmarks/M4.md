# M4 Benchmark Comparison & Acceptance

Two things this milestone measures:

1. **Regression guard** — the same criterion suite as M1/M2/M3
   (`crates/humm-core/benches/export.rs`, `crates/humm-media/benches/decode.rs`,
   `crates/humm-whisper/benches/e2e.rs`, `crates/humm-gui/benches/table_scroll.rs`),
   re-run against the `docs/benchmarks/M3.md` baselines. Per `CLAUDE.md`, a
   regression on `e2e/decode_transcribe` (the real decode+transcribe path a
   user exercises) is milestone-blocking.
2. **Two new M4 acceptance gates** — `crates/humm-gui/benches/viewer_scroll.rs`
   (the transcript **editor** table at 100k segments, ≥ 60 fps; spec §11) and
   the **windowed A/V-drift acceptance run** (F-083: p95 |audio − frame_ts| ≤
   50 ms over a 10-min fixture; spec §2.5/§11).

## Host

- Chip: Apple M4 (10 cores: 4 performance + 6 efficiency) — same machine as
  M1/M2/M3.
- RAM: 32 GiB. macOS: 26.5.2 (build 25F84). Same as prior milestones.
- Rust profile: `[profile.release]` — `lto = "thin"`, `codegen-units = 1`
  (workspace root `Cargo.toml`, unchanged since M1).
- Model (e2e): whisper `tiny`, GGML, GPU (Metal) on — the real cached tiny
  model at `model_root()` (~74 MB `ggml-tiny.bin`).
- Fixture (e2e): Buzz's `whisper-french.mp3` testdata (`HUMM_BUZZ_TESTDATA`).
- Run **sandbox-lifted** (`dangerouslyDisableSandbox`), the same M1/M2/M3
  precedent: the sandboxed shell segfaults inside ggml's Metal allocator on
  GPU model load (an environment property of the sandbox, not of humm).

## 1. Transcription-path regression guard (the blocking gate)

| Bench | M3 median | M4 median | Δ | Regression? |
|---|---|---|---|---|
| **`e2e/decode_transcribe/whisper-french.mp3/tiny`** | **192.17 ms** | **187.2 ms** | **−2.5%** | **No — a small improvement, within noise** |

Full isolated `e2e` output (two reproducing runs on a quiet machine):

```
e2e/decode_transcribe/whisper-french.mp3/tiny   time: [186.56 ms 187.26 ms 187.73 ms]
e2e/decode_transcribe/whisper-french.mp3/tiny   time: [186.59 ms 187.18 ms 187.77 ms]
                                                change: No change in performance detected (p = 0.79)
```

**Verdict: no transcription-path regression.** Two independent reasons, each
sufficient:

- **Nothing in the transcription path changed functionally in M4.**
  `git diff 1f0cf3c..HEAD` (M3 close → M4 tip) touches the transcribe/decode
  path in exactly two files, both non-functional: `humm-core/src/pipeline.rs`
  is `#[cfg(test)]`-only (a mock gained the new `decode_playback` trait method;
  `MediaInfo` test fixtures gained `video: None`), and `humm-media/src/decode.rs`
  is a **behavior-preserving refactor** — the shared ffmpeg streaming loop was
  extracted into `run_ffmpeg_pcm`, called by both `decode` (unchanged args:
  `-ar 16000`, `pcm_f32le`, same read loop, same `bytes_to_f32`) and the new
  `decode_playback`. `WhisperEngine` is untouched. With no functional change in
  the path the bench exercises, any delta is by definition environmental.
- **The measured number is a small *improvement*, tightly reproduced.** Two
  isolated runs on a quiet machine landed at 187.26 ms and 187.18 ms — a ±0.6 ms
  CI, criterion's own "No change in performance detected" (p = 0.79) between
  them — both below M3's 192.17 ms.

**A note on run-to-run variance (the M3 pattern, again).** During Task 14's
active benchmarking (back-to-back release compiles, then a 10-min windowed GUI
playback run consuming CPU/GPU), interleaved `e2e` runs read as high as
350–370 ms — and criterion's own comparison flipped between "regressed" and
"improved" by ±48% *on the same unchanged binary* between consecutive runs.
This is the identical thermal/contention signature M3.md documented (its 222 ms
outlier that a bare isolated re-run erased to 191 ms): "the developer's primary
laptop, not an isolated benchmark rig" (M1.md's words). The trustworthy figure
is the quiet-machine isolated run — 187 ms, reproduced twice — since throttling
only ever *slows* the number, never speeds it; a reading below M3's is
impossible to explain as a masked regression.

Supporting benches (`export`, `decode`, `table_scroll`) were not re-measured
this milestone — none of their source changed since M3 (`export`/`decode`
untouched; `table_scroll` is the M3 gate, still passing), and only `e2e` is the
regression-blocking path per `CLAUDE.md`.

## 2. `viewer_scroll` — 100k-segment editor-table scroll (new M4 acceptance gate)

`crates/humm-gui/benches/viewer_scroll.rs` drives the **real**
`humm_gui::views::viewer_table::ui` (the segment **editor** table an open
transcript renders in Timestamps mode — heavier per-row than the M3 task
table: 4-text-line rows of `Start | End | Text | Translation` interactive
cells) inside a headless `egui::Context`, over a synthetic 100 000-row
`ViewerVm` (`ViewerVm::for_bench`, mirroring the M3 `TasksVm::for_bench`), with
injected `MouseWheel` scroll gestures sweeping the full content range. It is the
editor-table sibling of M3's `table_scroll.rs` and reuses that file's exact
`egui_extras` scroll-state `Id`-reconstruction for its pre-measurement sanity
check (proving the rendered row range genuinely advances before any number is
trusted — it does: 30 fling frames moved the rendered range from ~row 0 to
~row 11 600, row height 59.9 pt).

| Measurement | Value | Milestone target | Verdict |
|---|---|---|---|
| Criterion median (95% CI) | 326.10 µs (317.87–334.57 µs) | — | — |
| **Manual sampling, p95** (300 frames, no criterion) | **549.04 µs** | **< 16.6 ms (≈60 fps)** | **PASS**, 30.2× margin |
| Manual sampling, mean | 476.89 µs | — | — |
| Manual sampling, max | 2.275 ms | — | still 7.3× under target |

```
viewer_scroll/viewer_scroll_100k   time: [317.87 µs 326.10 µs 334.57 µs]
viewer_scroll_100k manual sampling (300 frames): mean=476.891µs p95=549.042µs max=2.275375ms
viewer_scroll_100k acceptance verdict: PASS (p95 < 16.6ms)
```

Criterion reports mean/median only, so the bench separately times 300 frames by
hand for the p95 the acceptance criterion is stated in (same pattern as
`table_scroll.rs`). Both the criterion and manual numbers clear the 16.6 ms
(60 fps) target by more than an order of magnitude — `egui_extras`'s row
virtualization keeps the heavier editor rows just as cheap at 100k as the task
table. Spec §11's "viewer table ≥ 60 fps at 100k segments" gate is satisfied.

## 3. A/V-drift acceptance — windowed, 10-min (new M4 gate, F-083)

The synced-playback acceptance the M4 spec pins (§2.5/§11): **p95
|audio_ms − frame_ts_ms| ≤ 50 ms over a 10-min run**. This exercises the whole
playback stack in a **real OS viewer window** on the unsandboxed machine — real
CoreAudio device, real ffmpeg-rawvideo frames, the audio-master A/V clock
(ADR-019) — which no headless test can reach (deferred egui viewport, single
root in kittest).

- **Fixture** (the spec's exact command):
  `ffmpeg -f lavfi -i testsrc2=duration=600:rate=25 -f lavfi -i sine=frequency=440:duration=600 -shortest -pix_fmt yuv420p av-drift-600s.mp4`
  (26 MB, 600 s, 25 fps video + 440 Hz tone).
- **Method:** launched the real debug `humm-gui` binary sandbox-lifted with
  temp `HUMM_*` dirs and the test-only hooks
  `HUMM_SMOKE_OPEN_VIEWER=<fixture>` + `HUMM_SMOKE_AV_DRIFT_LOG=<csv>`
  (`docs/HUMM_SURFACE.md` §5.1). The hook seeded a Completed transcript row for
  the fixture, opened its viewer through the normal `open_viewer` path (a real
  OS window — confirmed a foreground GUI process; wgpu Metal surface + a named
  viewport `av-drift-600s.mp4` in the logs), auto-started playback, and closed
  the app at end-of-media. Each rendered video frame appended one
  `audio_ms,frame_ts_ms` pair (audio position = the A/V master clock, vs the
  displayed frame's presentation timestamp) via `ViewerVm::record_drift`. The
  process exited 0 after ~11.4 min (≈90 s whole-file decode + 600 s playback).
- **Parse:** `|audio_ms − frame_ts_ms|` over every logged frame.

| Metric | Value |
|---|---|
| Frames (drift pairs) logged | **35 060** |
| Audio position span | 23 – 600 003 ms (full 600 s) |
| Mean | 18.61 ms |
| Median | 18 ms |
| p90 | 34 ms |
| **p95** | **37 ms** |
| p99 | 40 ms |
| max | 5067 ms (a single transient stall) |
| Frames > 50 ms | **3 of 35 060 (0.01%)** |
| **Gate (p95 ≤ 50 ms)** | **PASS** |

**Verdict: PASS.** p95 = 37 ms, comfortably inside the 50 ms gate, with only 3
frames of 35 060 (0.01%) exceeding it. The lone 5067 ms max is a single
transient frame-reader stall (an ffmpeg-rawvideo hiccup / OS scheduling blip);
it moves neither p95 nor p99 (37 / 40 ms). This validates ADR-019's structural
decision — a **single audio master clock** with the video pane sampling the
frame for the current audio position each repaint holds sub-50-ms sync across a
full 10-min run **with no drift-correction loop at all**, unlike Buzz's two
independent clocks corrected every 100–200 ms.

A shorter 20 s validation run (same hooks, `av-drift-20s.mp4`) was executed
first to de-risk the mechanism: 1201 frames, p95 = 38 ms, max = 55 ms — same
result shape, confirming the hook + drift log work end to end.

## Reproducing

```bash
export CARGO_HOME="$(git rev-parse --show-toplevel)/.cargo-home"

# Regression guard + viewer_scroll gate (isolated runs recommended for e2e):
cargo bench -p humm-whisper --bench e2e            # needs ffmpeg + real tiny model, sandbox-lifted
cargo bench -p humm-gui     --bench viewer_scroll  # no external prerequisites

# A/V-drift acceptance (real window; sandbox-lifted, macOS with a display + audio device):
ffmpeg -f lavfi -i testsrc2=duration=600:rate=25 -f lavfi -i sine=frequency=440:duration=600 \
       -shortest -pix_fmt yuv420p /tmp/av-drift-600s.mp4
HUMM_SMOKE_OPEN_VIEWER=/tmp/av-drift-600s.mp4 HUMM_SMOKE_AV_DRIFT_LOG=/tmp/drift.csv \
  HUMM_DATA_DIR=... HUMM_CONFIG_DIR=... cargo run -p humm-gui
# then: p95 of |audio_ms - frame_ts_ms| over /tmp/drift.csv  (see the parse above)
```

Same skip behavior as prior milestones: `e2e` prints a line and registers no
measurements (exit 0) when ffmpeg, the Buzz testdata, or a real cached `tiny`
model is unavailable; `viewer_scroll` always runs (no external prerequisites).
