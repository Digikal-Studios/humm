## 1. Call-path innocence (`git diff 0864269..HEAD`) — done first, before any bench

`git diff 0864269..HEAD --stat -- crates/humm-core/src/pipeline.rs
crates/humm-core/src/queue.rs crates/humm-whisper/
crates/humm-media/src/decode.rs` names four files. Every hunk, classified:

### 1.1 `crates/humm-core/src/pipeline.rs` — `move_file` back-port, not on the transcribe path

The diff extracts `move_file`'s cross-device-rename fallback arm into a new
`move_file_via_copy`, which now delegates to `crate::fsutil::copy_then_rename`
(the same primitive `humm-media::demucs`'s own already-fixed `move_file`
uses — a genuine back-port, D5b-13) instead of the old inline
`fs::copy` + `fs::remove_file` pair. One new unit test
(`move_file_fallback_removes_source_after_copy`) pins it directly, since the
real `EXDEV` failure can't be forced from a single-tempdir test (documented
in the function's own doc comment).

**This is not on the transcribe path.** `move_file` is called from exactly
one place, `apply_source_disposition` (line 393), which is itself gated:

```rust
if let Some(disposition) = job.output.source_disposition {
    apply_source_disposition(disposition, &job.input, job.output.directory.as_deref());
}
```

`source_disposition` is `Some` only for folder-watch jobs (F-030); the CLI's
`humm add <file> --txt -s small` invocation this task's e2e bench runs never
sets it, so this whole function — and therefore `move_file`/
`move_file_via_copy` — is never reached on the bench's path. Confirmed by
reading the call site, not assumed from the brief's prediction.

### 1.2 `crates/humm-core/src/queue.rs` — doc-comment only

The entire diff is a rewrite of one module-doc paragraph, updating the
"single writer" invariant's explanation to describe M9 Task 2's
(`copy_replaced_completed`) one-transaction path alongside the pre-existing
`copy_transcription` + `mark_replaced_completed` pair. **Zero executable-code
changes** — confirmed by the diff itself (every `+`/`-` line is inside a
`//!` doc block).

### 1.3 `crates/humm-media/src/decode.rs` — stderr-tail helper swap; reader thread already existed pre-M9

The diff replaces an inline `thread::spawn(move || { stderr.read_to_end(...) })`
with `crate::stderr::spawn_stderr_tail(stderr)`, a new shared helper
(`crates/humm-media/src/stderr.rs`, added this milestone, D5b-1/D5b-5) that
unifies `decode.rs`/`encode.rs` onto the same bounded-tail capture
`demucs.rs`/`fetch.rs` already had (`STDERR_TAIL_CAP = 2 * 1024` bytes,
keeping the *last* 2 KB rather than accumulating unboundedly).

**Checked, not assumed: the background reader thread is not new on the
happy path.** The pre-M9 code already spawned `stderr_handle` unconditionally
— right after `stdout`/`stderr` are taken from the child, before the main
stdout-read loop starts, regardless of whether the child ultimately
succeeds or fails (`decode.rs` pre-M9, lines around the old
`let stderr_handle = thread::spawn(...)`). Both old and new code join that
thread exactly once, either in the cancellation branch or after the main
loop's `child.wait()`. So this is a same-shape swap, not a new thread on a
path that didn't have one:

- **What changed**: the read pattern (old: one `Read::read_to_end` call,
  which itself loops internally on a growing `Vec`; new: an explicit
  `read()` loop over a fixed 4 KB scratch buffer, draining into a
  capped-and-trimmed `Vec`) and the memory bound (old: unbounded; new: 2 KB
  tail). The UTF-8-decode-and-`trim` conversion also moved from
  "computed only inside the `if !status.success()` branch" (old) to
  "computed unconditionally, inside the thread, every call" (new, since
  `spawn_stderr_tail`'s thread body always finishes with the string
  conversion before returning).
- **Why it's negligible on this bench's path**: both `decode_mono_at` call
  sites (`decode`/`decode_playback`) pass `-loglevel error` to ffmpeg, so on
  a clean decode of a real fixture, ffmpeg writes **nothing** to stderr —
  the buffer stays empty on the happy path either way, and the "always
  compute the trim" change costs a `String::from_utf8_lossy` +
  `.trim().to_string()` over an empty `Vec`, which is not measurable
  against the dominant cost (reading the actual PCM stream off `stdout`,
  64 KB at a time). Confirmed by reading `decode_mono_at`'s ffmpeg argument
  list directly, not assumed.
- **Classification: bounded-tail hardening, functionally inert on the happy
  path of this bench.** §3.1 measures it directly (same-day, paired) rather
  than resting on this argument alone.

### 1.4 `crates/humm-whisper/Cargo.toml` — version metadata only

`version = "0.1.0"` → `version.workspace = true`, and the `humm-media` path
dependency's declared version `"0.1.0"` → `"1.0.0"`. Both are Cargo
manifest fields with no effect on compiled code; confirmed indirectly by
the M9/M8 binaries otherwise behaving identically on the criterion `decode`
bench (§3.1) and byte-identically on the real e2e transcript (§2.1).

### 1.5 Verdict

**No hot-path change that runs by default.** `pipeline.rs`'s only change is
gated behind a folder-watch-only `Option` the CLI's default invocation
never sets; `queue.rs`'s diff is prose only; `decode.rs`'s diff is a
bounded-tail refactor whose extra work is unconditionally empty-buffer on
a clean decode (both old and new code already ran a background reader
thread on the happy path — not a new addition); `humm-whisper/Cargo.toml`
is metadata. Not BLOCKED — proceeding to measurement.

## 2. Transcription-path regression guard (the blocking gate)

### 2.1 Real product-path run: `humm add` on `audio-long.mp3`, `small` model

Method: `/usr/bin/time -l <binary> add <fixture> --txt -s small -d <outdir>
--quiet`, fresh isolated `HUMM_DATA_DIR`/`HUMM_CONFIG_DIR`/`HUMM_LOG_DIR`/
output directory per run, sandbox-disabled (GPU/Metal — M1–M8 precedent),
`caffeinate -dimsu` running for the whole session, ≥1 s settle between
runs. 3 interleaved pairs, alternating order (M9→M8, M8→M9, M9→M8), per the
task brief. Both binaries built once (`cargo build --release -p humm-cli`)
before any timed run.

| Pair | Order | M9 wall | M8 wall | M9 peak RSS | M8 peak RSS | Load (before) |
|---|---|---|---|---|---|---|
| A | M9→M8 | 17.94 s | 20.94 s | 1107.03 MB | 1107.38 MB | 4.62 / 4.42 |
| B | M8→M9 | 10.04 s | 11.86 s | 1090.01 MB | 908.28 MB | 5.57 / 5.21 |
| C | M9→M8 | 7.45 s | 9.99 s | 904.33 MB | 1100.20 MB | 4.60 / 3.90 |

Every run exited 0 and wrote a `.txt` transcript. **Pair A's two transcripts
are byte-identical** (`md5 eec661f3…` both sides) — checked directly as a
correctness cross-check beyond this doc's own scope (transcript text is
normally out of scope for a diff, but identical text on identical model +
identical input is a clean confirmation neither side silently diverged).
All six transcripts are the same size (1404 bytes), consistent with
deterministic decoding on this model/input pair.

**Pair A is flagged as an outlier pair** — both its readings (M9 17.94 s,
M8 20.94 s) run 2.1–2.4× every other reading in this table (Pair C's
7.45 s/9.99 s, the tightest pair), yet `uptime` load immediately before
Pair A (4.62/4.42) was *not* elevated relative to Pair B (5.57/5.21) or C
(4.60/3.90) — so machine contention alone doesn't explain it. This is a
proportionally larger swing than either criterion outlier flagged in §3,
and the most credible explanation is a **cold-start effect specific to
Pair A**: it is the first invocation of *both* freshly-built binaries in
this bench session — first `dyld` link, first page-in of the binary's own
text/data segments, first Metal/Core ML pipeline compilation and model
upload for each process, none of which repeat on Pair B/C's invocations of
those same now-warm binaries. Per the M7/M8 convention (flag, don't blend),
both a pooled-all and a Pair-A-excluded figure are reported:

- **Wall clock, pooled over all 3 pairs**: M9 11.81 s
  ((17.94+10.04+7.45)/3), M8 14.263 s ((20.94+11.86+9.99)/3) → M9 ~17.2 %
  faster, pooled.
- **Wall clock, Pair A excluded (B+C only)**: M9 8.745 s ((10.04+7.45)/2),
  M8 10.925 s ((11.86+9.99)/2) → **M9 ~20.0 % faster**, and still faster in
  both remaining pairs, no sign flips either way. With only 2–3 single-shot
  samples per side (no internal CI the way criterion's samples give §3),
  **both pooled figures are imprecise point estimates**, not
  statistically tight ones — reported for completeness, not as a precise
  percentage to hang a claim on.
- **Peak RSS, pooled over all 3 pairs**: M9 1033.79 MB, M8 1038.62 MB
  (Pair A excluded: M9 997.17 MB, M8 1004.24 MB) → **essentially parity
  either way** (well under 1 % difference). Direction flips pair-to-pair
  (B: M8 lower; C: M9 lower) with no consistent side — expected, since both
  binaries load the identical cached `small` GGML model and this default
  invocation never reaches the noise-reduction/isolation code (§1.5), so
  RSS is dominated by the shared whisper.cpp/Metal working set on both
  sides, same finding shape as `MISSION.md` §3's humm-vs-Buzz parity
  result.

**The residual speedup (M9 faster in every pair, ~17–20 % pooled either
way) is real but unattributed, and is not claimed as evidence of a specific
improvement.** §1's own call-path innocence analysis found nothing on this
path that should make M9 measurably faster than M8 — a gated-off
`move_file` back-port and a stderr-capture swap that's empty-buffer on the
happy path predict statistical indistinguishability, not a consistent
~20 % gap. Concretely checked one candidate cause and ruled it out:
`git diff 0864269..HEAD -- Cargo.toml` shows `[profile.release]`
(`lto = "thin"`, `codegen-units = 1`) is untouched — so this isn't a
build-profile change. Candidate mechanisms that were **not** independently
verified and are named here explicitly as speculation, not findings: the
workspace-wide `0.1.0` → `1.0.0` version bump and the new `xtask` workspace
member (§1.4) altering codegen/linker layout in some way that doesn't show
up in `[profile.release]`; cache/thermal-state differences between this
worktree's `target/` (reused and incrementally rebuilt across many prior
M9 tasks this session) and `m8-bench-tip`'s (a single fresh build); or
allocator/page-layout effects from the two binaries' different link
histories. None of these were tested against each other, so none is
claimed as the cause — the honest statement is: no regression, a real and
repeatable-this-session speedup exists, its source is unknown.

### 2.2 Verdict

**No transcription-path regression. Gate: PASS.** M9 is consistently at
least as fast as (and, in every pair measured, faster than) a same-day
M8-tip checkout, and at RSS parity, on the real CLI path with the real
cached model against Buzz's own fixture. Combined with §1's call-path
innocence (nothing on this path changed except a gated-off `move_file`
back-port and a functionally-inert stderr-capture swap), there is no basis
to treat this milestone's changes as a regression — but per the note above,
the residual speedup itself is unexplained and is not claimed as a
verified improvement, only as evidence against a regression.

## 5. Bottom line

**PASS — no transcription-path regression.** Three independent lines of
evidence, all negative for a regression:

- **Code** (§1): the only unconditional change on the files that could
  touch the transcribe path is a bounded-tail stderr-capture swap that is
  empty-buffer on every clean decode (ffmpeg runs `-loglevel error`); the
  other two hot-path-adjacent changes are a gated-off (`Option::None` on
  the CLI's default path) folder-watch `move_file` back-port and a
  doc-comment-only rewrite.
- **Real product-path measurement** (§2): M9 faster in all 3 interleaved
  pairs (pooled 11.81 s vs 14.263 s, ~17.2 % faster; 8.745 s vs 10.925 s,
  ~20.0 % faster with the flagged Pair-A outlier excluded — same
  direction, both imprecise point estimates), peak RSS at parity in both
  treatments (well under 1 % difference, direction inconsistent
  pair-to-pair — noise, not a trend), transcripts byte-identical where
  checked. **This speedup is unattributed** — §1's innocence analysis
  predicts near-parity, not a consistent ~20 % gap, and no candidate cause
  was independently verified (one, a build-profile change, was checked and
  ruled out). No regression; the residual speedup is unexplained and not
  claimed as a verified improvement.
- **Criterion suite** (§3): `decode` and `export` both show no regression
  once each table's own single-pair outlier (independently explained by a
  scheduler/load spike, not by any code difference) is excluded; the
  cross-session comparison against `M8.md`'s recorded numbers is
  explicitly flagged as confounded by that session's much heavier load and
  is not treated as a regression signal.

No fix required before Task 18.
