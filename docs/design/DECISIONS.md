Format: context → options → decision → rationale → validation. Versions checked against crates.io 2026-07-20. Standing Policy defaults each get an ADR with their validation plan/result.

## ADR-001 — Cargo workspace with adapter crates per non-Rust boundary
**Options:** single crate with modules; workspace (core + adapters + thin binaries).
**Decision:** workspace as laid out in `ARCHITECTURE.md` §1.
**Rationale:** Standing Policy isolation rules; independent compile units (whisper.cpp C build isolated); per-adapter contract-test suites make external upgrades verifiable alone. Pure-Rust services stay in core — adapter crates are for non-Rust boundaries only.

## ADR-002 — Whisper inference via `whisper-rs` (0.16.0), validated against `candle`
**Options:** whisper-rs (FFI to whisper.cpp); candle (pure-Rust HF); burn; onnxruntime whisper.
**Decision:** `whisper-rs` with `metal` + `coreml` features on Apple Silicon (pre-approved default).
**Rationale:** whisper.cpp is the performance reference for local Whisper on Apple hardware (Metal + CoreML-encoder); ggml model ecosystem gives Buzz-model compatibility (same files Buzz downloads, F-042/043); bundled/vendored C pinned by crate version (Policy rule 4).
**Verified during design:** whisper-rs 0.16.0 exposes the VAD API (`set_vad_model_path`, `enable_vad`, `WhisperVadParams`, `WhisperVadContext`, `whisper_vad.rs`), abort callback (cooperative cancel), and segment/progress callbacks (streaming sink) — F-045 needs no extra dependency.
**Corrected during M1 implementation (Task 6 — humm-whisper):** three empirical findings that revise the design-time notes:
1. **VAD via `FullParams` is inert through whisper-rs.** `enable_vad`/`set_vad_model_path` are only honored by whisper.cpp's context-level `whisper_full`; whisper-rs 0.16 wraps only `whisper_full_with_state`, which has no VAD path (confirmed empirically: with the flags set, no VAD ran and output equalled VAD-off, and in the vendored `whisper.cpp` 1.8.3 `if (params.vad)` lives only in `whisper_full`/`whisper_full_parallel`). F-045 is therefore implemented by driving the **standalone `WhisperVadContext`** directly: detect speech spans, transcribe the speech-only audio, and remap all segment+token timestamps back to the original timeline (`VadRemap`, humm's parity realization of Buzz's `_make_offset_mapper`). whisper.cpp *does* remap segment timestamps internally, but only inside `whisper_full`, and never remaps token timestamps.
2. **`set_abort_callback_safe` is miscompiled in whisper-rs 0.16.0** — it instantiates its trampoline with the raw closure type `F` while the user-data is a `Box<dyn FnMut() -> bool>` (the progress/segment setters correctly use the boxed type), so it reinterprets a fat pointer as the closure and calls garbage, intermittently aborting the encoder (whisper error `-6`) even with nothing cancelled. Worked around with the raw `set_abort_callback` + `set_abort_callback_user_data` setters and a documented trampoline (the one intentional `unsafe` beyond the FFI transmute).
3. **Whisper-cli sampling default is beam search, `beam_size = 5`, `patience = -1.0`** (whisper.cpp 1.8.3 `examples/cli/cli.cpp`: `strategy = (beam_size > 1 || use_grammar) ? BEAM_SEARCH : GREEDY`); humm mirrors it for Buzz parity.
**Validation plan (M1, required):** benchmark vs candle's whisper example on the same ggml/safetensors model (small + large-v3-turbo) over `buzz/testdata/audio-long.mp3`: wall-clock, peak RSS, WER-proxy (diff vs reference transcript). Numbers recorded here. Abort if candle wins decisively (not expected on Metal).
**Validation result (M1):** executed the plan on Apple M4 / 32 GiB / macOS 26.5.2, both engines on **Metal**, over `audio-long.mp3` decoded to 16 kHz mono (119.99 s). humm = the shipped product path (`humm add … --txt`, whisper-rs `metal`+`coreml`, ggml **F16**). candle = its `whisper` example at tag **0.11.0** (commit `31f35b1`), `--features metal`, full safetensors **F32** (its `--quantized` path is `unimplemented!` for these sizes, so full weights is the fair *and* forced match; F32 gives candle the heavier-precision benefit of the doubt). Same measurement scope both sides (`/usr/bin/time -l`, model-load-included wall + peak RSS, 1 warm-up + 2 measured runs; first download/compile run excluded on both sides). Full protocol + raw logs: `validation/adr-002/README.md`.

| Model | Engine | Wall (s, mean of 2) | Peak RSS (MiB) | Transcript agreement |
|---|---|---:|---:|---:|
| small | **whisper-rs** | **6.92** (17.3× RT) | **861** | 38.3 % pairwise vs candle |
| small | candle 0.11.0 | 13.20 (9.1× RT) | 1927 | — |
| large-v3-turbo | **whisper-rs** | **8.18** (14.7× RT) | **1820** | 36.2 % pairwise vs candle |
| large-v3-turbo | candle 0.11.0 | 16.07 (7.5× RT) | 3186 | — |

whisper-rs is **1.91×/1.96×** faster (small/turbo) and uses **2.24×/1.75×** less peak memory. The low pairwise agreement is candle's *minimalist example* emitting ~half the words — it drops whole 30 s windows (candle-small: silent 60–90 s; candle-turbo: silent 90–120 s + a hallucinated "Thank you." past end-of-audio) and flip-flops French↔English per window under `--task transcribe`, whereas whisper-rs produced a complete, language-stable transcript; where both cover the same span they agree near-verbatim. So candle is not higher-quality (it is less complete), and it is decisively slower and heavier. **Verdict: the pre-approved `whisper-rs` default is confirmed — candle did not win on any axis (speed, memory, or completeness).** CoreML first-load compile latency was observed but confounded by the model download (humm run 0: small 45.97 s / turbo 124.11 s vs ~6–8 s steady state) and could not be cleanly isolated; it is one-time (compiled encoder is cached) and is kept off the steady-state numbers above — risk-register item logged. candle 0.11.0's example needed a one-line build fix (pin its audio-loader dep to `symphonia 0.5.4`; upstream dep churn, candle inference code untouched) — recorded in the README.

## ADR-003 — Media decode/probe via ffmpeg/ffprobe subprocesses
**Options:** libav* bindings (ffmpeg-next); gstreamer; symphonia (pure Rust); ffmpeg CLI subprocess.
**Decision:** subprocess (pre-approved): decode `ffmpeg -i <in> -f f32le -ac 1 -ar 16000 -` → stdout pipe; probe `ffprobe -print_format json -show_format -show_streams`; video `-f rawvideo -pix_fmt rgba` stream.
**Rationale:** CLI surface stable for decades vs ABI churn in libav; one-shot batch decode makes process overhead (~10 ms) immaterial; symphonia lacks full container coverage (wmv/avi/ogm).
**Note:** Buzz pipes s16le then converts to f32 (`whisper_audio.py:19`); humm pipes f32le directly — identical result, one fewer conversion.
**Validation:** contract tests decode golden files (each supported extension) asserting sample-count/duration/PSNR vs known PCM; startup probe caches version+capabilities; decode-throughput criterion bench. Deviate to bindings only if the subprocess path benchmarks as a real bottleneck (not expected).

## ADR-006 — GUI framework: **egui/eframe 0.35**
**Needs from `USER_JOURNEYS.md`:** 5+ real OS windows (main/viewer/recording/preferences/presentation), virtualized editable segment table (100k rows), custom painting (audio meter, presentation view), streamed video frames as textures, synced playback UI, native file dialogs, drag-drop, 20 rebindable shortcuts, i18n, background-task progress without jank, accessibility.
**Options considered:**
- **iced 0.14** — Elm model is clean for this app-shape; but multi-window is young, table virtualization and custom-widget ergonomics lag, accessibility incomplete, slower release cadence.
- **Slint 1.17** — polished, good a11y, royalty-free desktop license; but DSL split poorly fits our churn-heavy custom surfaces (meter, table-editor, video), and the license story (GPL/royalty-free/commercial triad) is a needless liability for a personal OSS-adjacent app.
- **gpui** — Zed-proven performance; but API-unstable, sparsely documented, effectively in-tree for Zed; too risky as a foundation others must build on for years.
- **egui/eframe 0.35** — immediate mode; deferred viewports = real OS windows; `egui_extras` virtualized tables; custom painting and per-frame texture upload are first-class (exactly our meter/video needs); AccessKit integrated; `rfd` native dialogs; drag-drop supported; huge ecosystem/velocity.
**Decision:** **egui/eframe**.
**Rationale (criteria-only — requirement fit, then performance):**
- *Requirement coverage:* egui is the only candidate strong on **all four hard requirements simultaneously** — mature real-OS-window multi-viewport support, virtualized tables proven at 100k+ rows (`egui_extras`), first-class custom painting (audio meter at capture rate), and per-frame texture streaming (video). iced is weakest on virtualized tables and has the youngest multi-window; Slint's declarative DSL puts our three custom-drawn surfaces (meter, segment-table editor, video canvas) behind its canvas/image-buffer escape hatches — more boundary-crossing on exactly the surfaces we redraw most; gpui covers the requirements but its API instability, sparse documentation, and minimal accessibility story put *functional parity delivery* (value #1) at risk.
- *Performance (value #2):* on this app's GUI hot paths — segment-table scrolling, ~60 Hz meter repaint while recording, video frame upload — egui and gpui are the two strongest candidates; all four clear 60 fps for forms-and-tables workloads, and GUI rendering is not humm's bottleneck (inference/decode dominate). Idle cost, the classic immediate-mode objection, is eliminated by repaint-on-event (idle ≈ 0 CPU). gpui's raw-throughput edge does not convert into user-visible speed here, and it charges for that edge in parity risk.
- *Remaining criteria:* accessibility — egui (AccessKit integrated) and Slint lead; iced incomplete; gpui minimal. Native file dialogs — equal (`rfd`). Platform look-and-feel — Slint leads, but the parity baseline (Buzz on Qt/Fusion) is itself non-native, so this criterion cannot outweigh the requirement gaps above.
**Rejected:** gpui (perf-per-risk fails value #1), Slint (custom-surface friction; look-and-feel edge irrelevant to parity), iced (table/multi-window/a11y gaps).
**Validation:** M3 exit criteria include a 100k-segment table scroll benchmark (≥ 60 fps sustained) and a multi-window smoke test on macOS; if egui misses these targets the ADR reopens with the measured numbers.

## ADR-007 — CLI: `clap` v4 (derive), genuinely headless — logged deviation
**Options:** clap; lexopt/pico-args; reproduce Buzz's Qt parser semantics.
**Decision:** clap v4 derive. Grammar: flag *spelling* parity with Buzz's `add` (every flag in `EXTERNAL_SURFACE.md` §2 identical). Deviations (this ADR): (1) **headless** — no window, no display server needed (Buzz drives a hidden GUI); (2) real exit codes: `0` all succeeded, `1` usage/config error, `2` ≥1 task failed, **`130` ≥1 task canceled in the run** (any-canceled outranks any-failed; SIGINT/Ctrl-C cancels every task — first signal cancels, second exits immediately; 130 = 128+SIGINT shell convention, added M2 Task 11 — startup stale-row recovery flips a *prior* run's rows but does not drive the current invocation's code); (3) `--json` event-per-line output (schema in `HUMM_SURFACE.md`); (4) stderr progress bars (TTY-only). `--hide-gui` accepted as a no-op with a deprecation note (parity of acceptance, not behavior).
**Rationale:** headless CLI is the mission's explicit outcome-parity case; clap gives `--help` quality and env-var integration per project conventions.
**Validation:** CLI integration tests (invoke binary, assert files/exit codes/JSON schema); differential test vs Buzz `add` on the same file for produced artifacts.

## ADR-008 — Backend consolidation (pre-approved deviation, recorded)
Buzz exposes five backends (`FEATURE_INVENTORY.md` F-040/F-041). humm ships **two**: local whisper-rs + OpenAI-compatible API.
- **CTranslate2/faster-whisper: not ported** (Standing Policy directive).
- openai-whisper (.pt) and in-process HF Transformers: superseded — same user outcome (local Whisper inference) served faster by whisper-rs; ggml model set covers all Buzz sizes incl. lumii + custom (F-042).
- Custom HF Whisper-family repos: supported by fetching/converting ggml equivalents (approved Q-2). **Non-Whisper HF models (MMS/wav2vec2): out of scope** (approved Q-2); the MMS ISO-639-3 language UI is therefore dropped.
- Live whisper.cpp: in-process via whisper-rs streaming — **no `whisper-server` subprocess** (Buzz's localhost:3003 hack disappears; hallucination guards become native params).

**Custom-model mechanics (M2 Task 8, F-042 full — the concrete `resolve_hf_repo`/`ensure_custom_model` behavior the paragraph above summarizes):**
- **User ggml URL** (`-s custom`, `model_loader.py:656-675`): `ModelDownloader::ensure_custom_model(url, ...)` downloads/resumes `url` to the fixed cache slot `ggml-custom.bin` (`registry::custom_model_file_name`, equal to `ggml_file_name(ModelSize::Custom)`) via the same `ensure_artifact` resume/sentinel algorithm every other artifact uses (Task 7's HTTP seam), with `sha_repo: None` — a custom URL has no upstream digest to check against, matching Buzz's own `download_model_to_path(..., expected_sha256=None)` for this path (`model_loader.py:670-675`). The completeness sentinel is still written, so a repeat call is the usual network-free fast path.
- **HF repo id** (`-m huggingface --hfid <repo>`, approved Q-2 scope): `ModelDownloader::resolve_hf_repo(repo, coreml_encoder, ...)` has two arms:
  1. `repo` is `openai/whisper-<name>` and `<name>` parses as a known `ModelSize` (`registry::openai_whisper_model_size`, e.g. `tiny` … `large-v3-turbo`, `large` → `Large`) — these are the canonical OpenAI Whisper repos, whose ggml equivalent is just the ordinary whisper.cpp/lumii size; delegate to `resolve_model(size, coreml_encoder, ...)` verbatim (full CoreML support, same cache path as `-s <size>`). Only the exact `openai/` prefix triggers this — a fork or mirror falls to arm 2.
  2. Otherwise, list the repo's files via the HF Hub API (`GET {hf_base}/api/models/{repo}`, JSON `siblings[].rfilename` — distinct from the `tree/main` endpoint used for SHA lookups) and select ggml candidates: files matching `ggml-*.bin` are preferred; if none, every `.bin` file is a candidate (deliberately simple, no further name filtering). *Exactly one* candidate downloads from `{hf_base}/{repo}/resolve/main/{file}` to `registry::hf_repo_model_file_name(repo)` (`"ggml-hf-" + repo with '/' → '--' + ".bin"`) via `ensure_artifact` with `sha_repo: None` (this API exposes no per-file digest) and **no CoreML encoder** — `ResolvedModel::coreml_degraded` is always `false` here (not a transport degradation; third-party repos simply don't publish the encoder zip whisper.cpp's own repos do). *Multiple* candidates and *zero* candidates are both `ModelError::Unsupported`: multiple names every candidate file and directs the user to pick one explicitly via the custom-URL setting (`models.custom_model_url`) instead of `--hfid`; zero states plainly that only ggml-format Whisper-family repos are supported here, that non-Whisper repos (MMS/wav2vec2) are the approved Q-2 scope cut, and points at both whisper.cpp's model-conversion docs and the custom-URL setting as the way forward. A non-2xx response or a body that doesn't parse as the expected JSON shape is `ModelError::Http` naming the repo — both are transport-class failures with nothing useful to fall back to.
- MMS and other non-Whisper repos need no special-case code: a repo published `.safetensors`-only (no `.bin` sibling at all) lands in the zero-candidates arm directly — that message *is* the approved Q-2 scope cut, not an extra check. A repo that does publish a raw `pytorch_model.bin` (some Transformers repos still do) is, deliberately, not special-cased out of the fallback `*.bin` rule — the brief's controller decision is "keep it simple: all `.bin` files are candidates," so that file becomes the single candidate and downloads; whisper.cpp/whisper-rs then fails to load it (it isn't ggml) with an actionable model-load error at inference time instead of at resolve time. Either way the repo never produces a working non-Whisper transcription path, which is the scope cut's actual guarantee — only *where* the failure surfaces differs.

## ADR-017 — Single-instance coordination: two-tier advisory file lock
**Context:** every humm process flips stale `queued`/`in_progress` rows to `canceled` at startup (`SqliteStore::cancel_stale_tasks`), recovering from a crashed/killed prior process (`HUMM_SURFACE.md` §7). But if a *second* humm process starts while a first is still genuinely running, the second one's startup flip can race the first one's live `in_progress` row and cancel real, in-flight work out from under it. Buzz has no analogous problem (single Qt process, no CLI); this is a carried M2 ticket, closed in M3.
**Options:**
1. Leave the race as-is (status quo) — simple, but a `humm add` launched while another is running can silently cancel its sibling's work.
2. One global exclusive lock held for a process's whole lifetime — closes the race but serializes every `humm add` invocation, which is a regression: concurrent transcriptions from separate invocations is existing, desired behavior (the queue itself already serializes *execution*; invocations queuing independently is not the same thing).
3. **Two-tier advisory lock**: `instance.lock` decides *who may run the stale flip* (not who may run at all), separate from `gui.lock` which decides GUI single-window exclusivity — a different, stricter policy that has no CLI analogue.
**Decision:** option 3, both files `fd-lock`-based under `paths::data_dir()` (`crates/humm-core/src/instance.rs`):
- **`instance.lock`.** Every humm process (CLI `add`, GUI), at startup, attempts a non-blocking *exclusive* claim. Winning it proves no other humm process currently holds any claim, i.e. this process is the sole live instance, so it is safe to run `cancel_stale_tasks()`; it then **downgrades** to a shared claim held for the rest of the process's life, so a second `humm add` can start moments later and run fully concurrently — humm never serializes invocations, only the stale-flip *decision*. Losing the exclusive claim (another process already holds shared or exclusive) skips the flip entirely and takes a shared claim instead (shared claims never contend with each other). A lock-file I/O failure (e.g. an unwritable `data_dir`) falls back to the pre-ADR-017 unconditional flip rather than failing the run.
- **`gui.lock`.** A GUI-only, separate file: the GUI takes an exclusive claim and never downgrades it, so a second GUI launch's own attempt fails outright and it shows a native "humm is already running." dialog and exits 0 (`crates/humm-gui/src/main.rs`) — Buzz has no such guard (a second Buzz instance silently corrupts shared Qt/DB state); this is a humm-only ✚ deviation. GUI processes still participate in the `instance.lock` stale-flip protocol like any other humm process; `gui.lock` only ever governs GUI-window exclusivity.
**Rationale:** the two locks encode two genuinely different questions (`instance.lock`: "am I provably the only one, so may I clean up?"; `gui.lock`: "is there already a window?") — collapsing them into one lock/policy would force either serializing `humm add` (over-restrictive) or letting a second GUI silently race the first (under-restrictive).
**`Box::leak` rationale:** `fd_lock::RwLock::try_write`/`try_read` return guards borrowing `&mut self`/`&self`; both `InstanceGuard` variants must be plain, non-generic, lifetime-free types so every caller across two binaries can hold one for the rest of `main` without threading a lifetime through their own signatures. Rather than reach for a self-referential-struct crate for a problem this small, `RwLock<File>` is `Box::leak`ed once per process per lock (at most two leaked allocations, ever) so its guards can soundly borrow `'static` — not a leak in the "bug" sense, since the lock is meant to live exactly as long as the process anyway (`instance.rs`'s "Why the lock is deliberately leaked" doc section).
**The downgrade gap, and why it's benign by call-site ordering, not just by luck:** between dropping the exclusive guard and re-acquiring a shared one, a process briefly holds no claim at all; if another process's own exclusive attempt lands in that instant, both processes will believe themselves sole and both run `cancel_stale_tasks()`. This is benign, and not merely by a timing coincidence: at both call sites (`humm-cli/src/run.rs::execute` and `humm-gui/src/services.rs::init`), `acquire_instance_lock`/`apply_stale_flip` runs — and returns — strictly *before* that same process's first `enqueue`/`handle.enqueue` call (`run.rs`'s stale-flip block, line 148, precedes its `for file in &args.files { … handle.enqueue(…) }` loop's first `handle.enqueue` call at line 247; `services::init`'s `apply_stale_flip` call precedes `spawn_task_runner`/any GUI-side enqueue, which only happens later once the app is running and the user imports something). So nothing *this* process enqueues can look stale yet by the time any interloper's exclusive attempt could land in the gap — there is no genuinely-running row for a second sole-instance winner to wrongly cancel, only rows that predate both processes' startups, which is exactly the set both would correctly agree on.
**Validation:** `instance.rs`'s 5 unit tests (`first_acquire_is_sole_instance`, `second_acquire_while_first_held_is_not_sole`, `sole_again_after_first_released`, `gui_lock_exclusive_second_returns_none`, `lock_files_are_created_under_data_dir`) prove the claim/downgrade/independence semantics directly; `run.rs`'s `relaunch_flips_stale_in_progress_row_to_canceled` (cli-int, M2) and the sandbox-lifted `acceptance_kill9_leaves_recoverable_canceled_row` (M2 Task 11) prove the end-to-end stale-flip through the real CLI binary. Implementing commits: `6192be7` (protocol + `instance.rs`), `9648f88` (GUI `main.rs` wiring of both locks).

## ADR-018 — Store-write-failure policy: never abort a run
**Context:** `queue.rs`'s `Runner` writes every task's status transition to the store (`mark_started`/`mark_completed`/`mark_failed`/`mark_canceled`/`update_progress`/`update_file`). Any of those writes can fail independently of the transcription pipeline itself (disk full, permissions, a locked/corrupt database file) — a question orthogonal to whether the actual transcription succeeded.
**Options:**
1. Treat a store-write failure as fatal to the run (fail-fast) — the DB is load-bearing for history, so a write failure aborts the task (or the whole queue).
2. **Never abort a run on a store-write failure**; the pipeline outcome alone decides the task's terminal state, and the write failure is surfaced out-of-band (logged, plus an event) so subscribers can tell the user their history is stale/incomplete.
**Decision:** option 2.
**Rationale:** finishing (or genuinely failing) the transcription is what the user is waiting on; a DB hiccup recording that outcome is a *lesser* failure than losing the actual work in progress, and conflating the two would make a transient history-write blip capable of discarding a completed transcription. The task's terminal status is decided by the pipeline outcome, never by whether the store write for it happened to land.
**Mechanism:** every failed store write both logs (`log::warn!`) and emits `TaskEventKind::StoreWriteFailed { operation, detail }` — out of band, interleaving anywhere in a task's normal event sequence without changing that sequence (`queue.rs` module docs). Consumers: `humm-gui` shows a persistent, dismissible `StoreHealthBanner` ("humm couldn't record history updates — exports still complete; see the log file"), with a repeat-count suffix on further events and a fresh reappearance after dismiss-then-recur; `humm-cli` human mode prints one stderr warning per failure (`warning: history not recorded (<operation>): <detail>`); `--json` emits `{"event":"store_write_failed","task_id":…,"operation":…,"detail":…}` as an additive event (`HUMM_SURFACE.md` §3).
**Validation:** `queue.rs`'s `store_write_failure_emits_store_write_failed_event` unit test (M3, plus the panic-containment tests `engine_panic_fails_the_task_and_queue_survives`/`engine_panic_discards_cached_engine`/`engine_panic_before_acquisition_still_discards_cached_engine` proving the *run-continues* half of the policy under the adjacent panic-containment hardening); `humm-gui::viewmodel`'s `apply_store_write_failed_is_a_pure_log_noop` test (the event never mutates a row); `main_window.rs`'s 5 `StoreHealthBanner` state-machine unit tests (`banner_hidden_initially`/`banner_shows_base_message_on_first_event`/`banner_appends_counter_on_subsequent_events`/`dismiss_hides_and_resets_counter`/`dismissed_banner_reappears_fresh_on_next_event`) plus the kittest `store_write_failed_event_shows_the_banner_and_dismiss_clears_it` (`tests/kittest_actions.rs`) driving a real injected event through the real app; `humm-cli/src/run.rs`'s `json_store_write_failed_matches_schema` pins the `--json` shape byte-for-byte. Implementing commits: `6a1d515` (policy + core emission), `f7bc650` (self-review cleanup).

## ADR-019 — M4 playback architecture (in-memory decode, cpal `AudioOutput` boundary, linear-interp varispeed, audio-master A/V clock)
**Context:** F-083's synced audio/video playback (M4) needs sample-accurate seek and loop, a varispeed control that actually works (Buzz's `sounddevice` rate call landed on a muted `QMediaPlayer` — no working speed at all, ledger #2), and A/V sync tight enough to pass a ±50 ms/10-min acceptance gate. Buzz ran two independent clocks (a `QMediaPlayer` audio clock and a separate ffmpeg video clock) and drift-corrected between them every 100–200 ms. The playback engine is the new `humm-audio` adapter crate (ADR-005 deps: cpal 0.18 + rubato 4.0) built on core boundary traits.
**Options considered:**
- *Decode:* (a) a seekable streaming `PcmStream` (the `open_stream` sketch ARCHITECTURE §2 originally carried) — bounded memory, but a seek-respawn state machine whose latency the loop-wrap boundary and A/V clock would have to tolerate; (b) **whole-file in-memory PCM** (`PlaybackPcm { samples: Arc<[f32]>, channels, sample_rate }`) — trivial O(1) sample-exact seek/loop, ~1.27 GB/hour (identical to Buzz's numpy buffer).
- *Varispeed:* (a) a rubato polyphase/sinc resampler (highest audio quality); (b) **linear interpolation over a fractional source cursor** (pitch shifts with rate — the standard scrubbing tradeoff Buzz's own Qt fallback path also had).
- *A/V sync:* (a) reproduce Buzz's two-clock drift-correction; (b) **a single audio master clock** the video pane samples each repaint.
- *Seek publication:* (a) two independent atomics (position + a seek generation); (b) **one packed `AtomicU64` `{generation:24, frame:40}` published by a single CAS**.
**Decision:** whole-file in-memory decode (`FfmpegDecoder::decode_playback` → f32le stereo 44.1 kHz, Buzz `sounddevice_player.py:28-35` parity); cpal `AudioOutput`/`OutputStream` core-boundary traits with the device-rate rubato resample living **inside** `CpalOutput` (only where the rate is negotiated, never on the master-clock path); **linear-interpolation varispeed in `humm-audio::Player`**; a single audio master clock (`Player::position()` is the A/V clock the scrubber, follow-audio, and video pane all read); packed-atomic single-CAS seek publication; f32-only output devices.
**Rationale:**
- *Linear interpolation, not rubato, for varispeed (the adjudicated deviation).* The pinned contract is **sample-exact** frame accounting: after N output frames at speed s, the position has advanced exactly N·s source frames (±1), and the loop wraps `end → start` sample-exactly. A priming sinc/polyphase resampler consumes a *fixed extra delay-line* worth of input beyond N·s, offsetting the published position — and therefore both the loop-wrap boundary and the A/V master clock the ±50 ms gate keys off — by that constant. So varispeed uses a fractional cursor (`cursor += speed` per output frame; whole part published). rubato is retained where it is both correct and required by ADR-005: the fixed-ratio device-rate conversion inside `CpalOutput`, which never feeds the clock.
- *Whole-file in-memory (Buzz-equal memory).* Sample-exact seek/loop with zero latency and a trivial position model; a streaming decoder would add a seek-respawn state machine for no user-visible win at typical media lengths. Revisit if long-file playback surfaces (this is the amendment to ARCHITECTURE §2's `open_stream` sketch).
- *Single audio master clock.* Buzz's 100–200 ms drift-correction existed only to reconcile *two* clocks; humm has one, so the whole correction loop is structurally unnecessary — the video pane simply picks the frame for the current audio position each repaint (Buzz's own drain-stale/one-frame-tolerance selection rule, ported).
- *Packed single-CAS seek.* Two independent atomics leave a nanosecond window where the fill callback's end-of-buffer position store can clobber a concurrent UI seek with no later resync (a genuine, silent lost-seek). Encoding `{generation, frame}` in one word and publishing it with a single `compare_exchange` makes the seek's store and the fill's commit mutually exclusive by construction — a raced seek makes the CAS fail (dropped, the seek's own value already published) so a lost seek is impossible.
- *f32-only output.* humm's player produces f32; a device offering no f32 config degrades with an actionable `AudioError` (naming the device's actual format) rather than silently mis-playing — Standing Policy rule 6.
**Validation:** `humm-audio` unit tests over a `MockOutput` with a simulated clock — `position_advances_with_frames_consumed`, `seek_moves_position_and_playback_origin`, `loop_wraps_exactly_at_end_boundary`, `speed_two_consumes_double_source_frames`, `speed_clamped_to_bounds`, `pause_stops_frame_consumption`, `end_of_media_stops_and_pins_position`, `set_loop_none_clears_wrap`, plus the seek-race regressions `seek_during_fill_is_not_lost`/`seek_between_generation_check_and_commit_wins` and `resample_state_converts_rate_without_device` (the device-rate rubato branch); an `#[ignore]` cpal contract test opened a real CoreAudio device and fired the fill callback (sandbox-lifted). The A/V-master decision is validated end-to-end by the **windowed A/V-drift acceptance run** (Task 14, `docs/benchmarks/M4.md`): a 10-min `testsrc2`+`sine` fixture played through the real viewport with `HUMM_SMOKE_OPEN_VIEWER`/`HUMM_SMOKE_AV_DRIFT_LOG`, **p95 |audio_ms − frame_ts_ms| = 37 ms (≤ 50 ms gate)** over 35 060 frames (mean 18.6 ms, p99 40 ms) — the single-clock design holds the gate with no drift correction at all (exact numbers/method in `docs/benchmarks/M4.md`). Implementing tasks: M4 Task 5 (media boundary), Task 6 (`humm-audio`), Task 10 (GUI wiring).

## ADR-020 — Resize/merge transcript: native Rust port of srt_equalizer + a stable-ts subset (F-086)
**Context:** F-086's resizer window offers Extend-endings, **Resize** (subtitle line-length fit, word-timestamps *off*) and **Merge** (regroup, word-timestamps *on*). Buzz delegates these to two third-party Python libraries — `srt_equalizer` (line-length splitting) and `stable-ts` (`WhisperResult.regroup`) — pinned by Buzz's `uv.lock` to **srt_equalizer 0.1.10** (tag `v0.1.10`, itself depending on **srt 3.5.3**) and **stable-ts 2.19.1**. Porting them natively (rather than shelling out to a Python interpreter humm doesn't ship) keeps the Standing Policy's "no non-Rust runtime dependency without an ADR" intact.
**Options considered:**
- (a) Subprocess to a bundled Python + the two libs — a heavy runtime dependency (a whole interpreter + torch/numpy for stable-ts) for two pure-algorithm transforms; rejected on Standing Policy grounds.
- (b) **Native Rust ports** of the exact reachable algorithms, validated differentially against the genuine pinned Python.
**Decision:** native ports in `humm-core::resize` (srt_equalizer 0.1.10 `split_subtitle(method="punctuation")` + extend-endings) and `humm-core::regroup` (the stable-ts 2.19.1 `mg`/`sp`/`sl` subset), with the following faithfully-preserved semantics and one deliberate scope cut:
- *Decisecond unit quirk preserved.* Buzz feeds stable-ts timings as `ms / 100.0` "fake-seconds" (1 fake-second = 100 ms real), so the default `mg=0.2` merges gaps ≤ **20 ms real**, and emits `int(x * 100)` back to ms — a lossy truncation. The port reproduces this exactly (`regroup/mod.rs`: `ms / 100.0` in, `int(start*100)..int(end*100)` out) rather than "correcting" it, because byte-exact parity with Buzz's output is the target.
- *Parser scope cut with an actionable error.* stable-ts's `parse_regroup_algo` accepts ~20 ops; humm's UI only ever emits `mg` (merge-by-gap), `sp` (split-by-punctuation), and `sl` (split-by-length), so the parser supports exactly those three and returns `RegroupError::UnsupportedOp` — naming the offending op and the supported set — for anything else reachable via the **`HUMM_MERGE_REGROUP_RULE`** override. (ledger #8.)
- *Python numeric semantics ported.* `round()` is round-**half-to-even** (banker's rounding) and integer conversion is `int()` truncation-toward-zero — both ported verbatim (`resize::round_half_even`, the regroup truncation) since off-by-one-ms disagreements would otherwise fail the differential.
**Rationale:** the two transforms are pure functions over segment lists; a native port removes an entire language runtime from the dependency graph at the cost of tracing two pinned libraries' exact behavior once. The pinned reference versions are recorded here so a future upstream bump is a deliberate, re-differentiated act, not a silent drift.
**Validation (`unit + diff`):** per-op unit tests (30 `regroup::`, plus `resize::` cases incl. `round_half_even_matches_python`), **plus genuine Python-reference differential fixtures** committed under `crates/humm-core/tests/fixtures/` and regenerable from `validation/m4-differential/`:
- `gen_resize_fixtures.py` runs the **real** srt_equalizer 0.1.10 + srt 3.5.3 (both pure-Python, stdlib-only) over Buzz's exact call pattern → **12 `fixtures/resize/*.json`** the Rust `resize` tests assert byte-for-byte.
- `gen_regroup_fixtures.py` imports the **genuine** stable-ts 2.19.1 `result.py` via a synthetic-package/torch-stub bypass (`validation/m4-differential/stubs/` stubs torch/torchaudio/tqdm; **numpy is real**, the regroup path being pure-Python once imported) → **16 `fixtures/regroup/*.json`** incl. Buzz's full default UI string (`mg=0.2++42+1_sp=…_sl=42`) and a CJK case, asserted exactly. Both harnesses ran on this machine; the fixtures are committed and regenerable — the F-045-style "the reference actually ran, here's the harness" transparency, but here it succeeded rather than being environment-blocked. Implementing tasks: M4 Task 3 (resize port, `3158a87`), Task 4 (regroup port), Task 12 (GUI resizer).

## ADR-021 — Live-recording session architecture (F-060/F-061/F-062/F-064, Q-10)

**Context:** M5 ports Buzz's live-recording feature (`recording_transcriber.py` + `recording_transcriber_widget.py`) — device capture, silence-aware chunking, a rolling-prompt realtime transcription loop, three display modes, live export/upload, and a presentation window — onto humm's architecture. ADR-008 already ruled out Buzz's `whisper-server` subprocess for live inference ("in-process via whisper-rs streaming"); this ADR is that decision's follow-through: the concrete session/thread/persistence/hardening shape the M5 design spec (`docs/superpowers/specs/2026-07-23-m5-live-recording-design.md`) laid out and the implementation then earned.

**Options considered:**
- *Engine invocation:* (a) spawn Buzz's own `whisper-server` on localhost and POST chunks (parity-literal, but reproduces a process-management/HTTP hack humm has no reason to keep — ADR-008 already rejected this); (b) **in-process, per-chunk `WhisperEngine::transcribe_live` calls on the already-loaded context** — the engine loads once per session, each chunk is a fresh `state.full()` call with a live-specific `FullParams` set natively mirroring the server's launch flags.
- *Capture rate:* (a) reproduce Buzz's device-rate loop verbatim (the chunker's `n_batch_samples` varies by device, matching Buzz exactly but complicating every downstream consumer); (b) **resample to 16 kHz inside the capture adapter** (ADR-005's fallback path), so the chunker and everything above it always sees a fixed rate.
- *Meter data ownership:* (a) one owner for the whole `MeterSnapshot` (simplest, but conflates two genuinely different producers — the RT capture callback and the session/chunker loop — behind one lock-free surface with unclear write races); (b) **split ownership by field**: the capture adapter writes only `current_rms` per callback; the session/chunker layer writes `average_rms`/`queue_len` per accumulated batch — matching Buzz's own two-signal split (`RecordingAmplitudeListener` vs. the transcriber's own signals).
- *Persistence:* (a) match Buzz exactly — a live recording leaves no trace once the window closes; (b) **persist as a first-class `transcription` row** (Q-10, user-approved improvement) — insert at record-start, append one raw-segment row per accepted utterance, mark `Completed` at stop.
- *Stale-row recovery on a crashed live session:* (a) treat it like every other stale row — flip to `Canceled` at the next startup (simple, but the viewer's Completed/Skipped-only open gate would then permanently hide a partial transcript that is real, finished work); (b) **a live-recording-specific stale-flip arm**: `InProgress` + `Source::LiveRecording` flips to `Completed`, not `Canceled`.
- *Realtime-fit signal:* (a) ship with no feedback and let a too-slow model silently fall behind (b) **measure and persist a realtime ratio per model size** (§2.8 ✚), surfaced as an inline warning before the next recording starts.
- *Presentation window styling:* (a) no user-stylesheet override (drop the capability); (b) **a tolerant three-property CSS-subset parser** (`color`/`background-color`/`font-size`) reading a config-dir file, since egui has no HTML/CSS renderer to hand Buzz's real stylesheet to.

**Decision:** (b) in every case above.

**Rationale:**
- *In-process per-chunk calls.* One loaded `WhisperContext` for the whole session (loaded once, per spec §2.1); each chunk gets its own `state.full()` call so cancellation, error handling, and the rolling prompt are all per-call concerns with no server process, no HTTP round trip, and no port to manage. The cost — a fresh `create_state()` per chunk with no cross-chunk KV-cache warm start — is real and measured (see `docs/benchmarks/M5.md`'s live realtime-fit number, markedly below the M1 CLI benchmark's continuous-decode figure for the same model size) but was accepted deliberately: correctness and architectural simplicity (no subprocess lifecycle, no localhost port, no JSON-over-HTTP chunk protocol) outweigh chasing a lower per-chunk fixed cost, especially since the measured ratio still clears the ≥1.0× "sustains realtime" bar by a wide margin on this machine.
- *Adapter-side 16 kHz.* Buzz's device-rate loop was itself an artifact of its capture path never resampling; humm's `CpalCapture` already has a documented fallback resample branch for exactly this case (ADR-005), so reusing it for live capture means the chunker's constants (`n_batch_samples`, `keep_sample_seconds`) are simple fixed numbers instead of a per-device-rate calculation threaded through every consumer.
- *Split meter ownership.* Mirrors a real distinction in Buzz's own code (two different Qt signal sources) rather than inventing a single shared-state contract that would need an arbitrary tie-break for "who last wrote what." Each writer only ever touches the field it alone is responsible for — no locking, no races to reason about.
- *Persistence + live-aware stale-flip.* A live session with no record of ever happening is strictly worse than one that's recoverable; Q-10 was user-approved specifically because Buzz's own behavior here is a limitation, not a considered design ("don't have to" persist, not "must not"). The stale-flip arm follows directly: once a live row is a first-class transcription, a crash mid-recording should leave it in the *same* recoverable shape a crashed file-import task gets (F-029), not lock it behind a status the viewer refuses to open.
- *Measured-speed warning.* The M1 benchmark predicted comfortable headroom (§2.8's own note) but a prediction on one file-mode benchmark run is not the same claim as "this machine's live per-chunk path keeps up" — measuring the actual thing once and surfacing it beats asserting a number that was never checked against the mode it's meant to describe.
- *CSS subset.* Buzz's own default stylesheet only ever emits the three properties this parser understands (spec §2.6) — a full CSS engine would be effort spent on capability nothing in Buzz's actual shipped behavior exercises.

**Validation:**
- **Chunker/merge logic** (`unit`, device-free): `live::chunker`'s 22 tests (incl. the negative-slice keep-back corner, ledger #3) and `live::merge`'s 35 tests (incl. the genuine Python-reference differential fixture, `merge_matches_python_reference_fixtures`).
- **Session orchestration** (`unit`, fakes): `live::session`'s 13 tests (chunk cadence, silence-skip, rolling prompt, drop-behind, engine-error handling, cancel-mid-idle-pause, `LiveMeasurement` math) plus the benign-`Canceled`-exit fix (`b47c059`, ledger #4) and the `LiveEvent::Stopped`-carries-measurement shape (ledger #5).
- **Capture adapter** (`unit` device-free + `contract` device-attached): `humm-audio`'s 43 tests (conversion/downmix/RMS/resample-count math) + 3 `#[ignore]` contract tests against the real default input device — written and attempted sandbox-lifted, but blocked by the standing microphone-TCC environment issue (`.superpowers/sdd/task-5-report.md`); the native-rate probe (48 kHz, confirming the fallback resample path is the one that runs on this machine) did complete before the hang.
- **GUI wiring end to end** (`kittest`, no real hardware/network): `tests/kittest_recording.rs`'s `scripted_end_to_end_record_two_utterances_then_stop` (panel text, store row lifecycle incl. restart-survival via store reopen, TXT export bytes, upload call sequence) and `session_thread_panic_recovers_the_window_and_completes_the_store_row` (the crash-recovery fallback, ledger #6's teardown-ordering fix's paired regression test, `stopped_is_sent_only_after_capture_teardown_completes`).
- **Real windowed acceptance** (M5 Task 14, `docs/gui-manual/M5.md` + `docs/benchmarks/M5.md`): the mic-TCC blocker made a real-microphone run impossible in this environment, so acceptance ran instead against the **real** `WhisperEngine` (small model, Metal, the already-cached `ggml-small.bin`) fed **real, ffmpeg-decoded fixture audio** (Buzz's `audio-long.mp3`) at genuine wall-clock pace through a purpose-built `FixtureCapture` (`crates/humm-gui/src/live_fixture.rs`) driving the real recording window end to end (`HUMM_SMOKE_LIVE_FIXTURE`) — a real OS window (wgpu Metal surface confirmed in the logs), a real store row (34 real French-transcript segments persisted, verified surviving a full process restart), and a measured realtime ratio (1.87–2.53× across two 200 s runs, comfortably above the ≥1.0× bar) with the benign-`Canceled`-exit ledger item (#4) empirically observed firing at the exact Stop instant with no error surfaced to the user.
