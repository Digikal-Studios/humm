## 0. How these runs were driven (and three new harness facts)

Same capability set M7 established — `screencapture` for window images,
synthetic `CGEvent` mouse/keyboard (never System Events `click at`), System
Events only for reading the AX tree. Three things this pass had to learn on
top of it, recorded so the next pass does not rediscover them:

1. **Window ids are not stable.** A deferred viewport (Preferences, viewer,
   Speaker-ID) gets a *new* `CGWindowID` across repaint/resize cycles;
   `screencapture -l<id>` fails with `could not create image from window`
   after that. Every capture in this pass re-reads
   `CGWindowListCopyWindowInfo` first and matches by title.
2. **Tooltips need frames.** egui only paints a hover tooltip after the hover
   timer elapses, and a window that receives no input stops producing frames.
   A single synthetic `mouseMoved` therefore never shows one; a ~2 s jiggle
   (8 × 1-pixel moves inside the widget) does. Both tooltips in this document
   (§1a item 6, §3 item 22) were captured that way.
3. **In-window menus close quickly.** Clicking `File`/`Help` opens the menu on
   *release*, and it is gone by the time a 1 s-delayed screenshot runs; the
   capture has to be issued immediately after the click.

Unchanged from v5 §0: API keys are never typed into fields (policy), native OS
dialogs are not driven (a native panel may be *opened* and dismissed with Esc,
which §6/F-020 does), and human-judgment items stay human.

## 8. Findings from this pass

### 8.1 A viewer's Identify-Speakers click does nothing until the *root* window gets input — `FAIL`

`views/viewer.rs:345` sets `vm.identify_speakers_requested`; the harvest that
turns it into a window (`app.rs:2429-2443`) runs in the **root** viewport's
update pass. Nothing requests a root repaint when the flag is set, and a
deferred viewport's own repaints do not drive the root. Observed: the click
landed (the button showed its pressed frame), then ~90 s and several pointer
moves *over the viewer window* passed with no window appearing; the
Speaker-ID viewport was created within ~1 s of the first pointer move over the
**main** window (`Creating new viewport "A950"`, 16:40:27).

A user who clicks `Identify Speakers` and keeps the mouse in the viewer sees
nothing happen at all. The one-line fix shape is a
`ctx.request_repaint_of(ViewportId::ROOT)` at the flag-setting site.
`resize_requested` is harvested by the identical loop three lines above
(`app.rs:2425-2427`), so the Resize button is presumed to share the defect —
that half is **inference, not observation**; this pass did not click Resize.

**Fixed (Task 17, F-087).** Both `resize_requested` and
`identify_speakers_requested` are latched through a new
`views::viewer::latch_root_harvested_intent` helper that also calls
`ctx.request_repaint_of(egui::ViewportId::ROOT)` at the click site — the
inverse of `HummApp::repaint_other_open_viewports`'s root-to-children wake
(root → children there, child → root here). The Resize button shared the
defect exactly as inferred; both are fixed by the same helper. Unit-pinned
(`views::viewer::tests::latch_root_harvested_intent_requests_a_root_repaint`)
and windowed-re-verified — §12.

### 8.2 The model-download **Cancel** button is unreachable — `FAIL`

`models_ui.rs:407-419` renders, in one horizontal row, a `ProgressBar` with no
`desired_width` followed by the Cancel button. `ProgressBar` defaults to
*all remaining width*, so the button is always laid out past the right edge
and is never visible or clickable. Observed at the 650 pt minimum width
`[26]` and again after widening the window to 901 pt `[27]` — widening does
not help, because the bar simply grows with it. Both the indeterminate and the
determinate (`0 %`, `80 %`, `81 %`) states show the same thing.

Consequence: a started model download — up to 1.5 GB — cannot be stopped from
the UI at all; the only way out is quitting the app (which is what this pass
had to do, leaving a `.partial` behind, since a SIGKILL cannot run the
cleanup). The kittest coverage does not catch it because the harness clicks by
widget id, not by pixel. Fix shape: give the bar an explicit
`desired_width(…)` (or lay the Cancel button out first / put the row in a
`with_layout(Layout::right_to_left(...))`).

This is the F-044 row's own *"a live download with cancel"* item, so §7.6 of
the design is **not** fully satisfied: download and delete are, cancel is not.

**Fixed (Task 17, F-044).** The `Downloading` row now wraps the bar + Cancel
button in `ui.with_layout(egui::Layout::right_to_left(egui::Align::Center),
...)` — Cancel is allocated first (its own natural width, rightmost), then
the bar fills whatever's left via `ui.available_size_before_wrap()`, which by
then correctly excludes the button's space. Same shape `recording.rs`'s
Record/meter row already used for the identical "egui has no automatic flex
layout" reason. Kittest-pinned by rendered geometry, not id-based `.click()`
(`downloading_row_cancel_button_stays_within_the_650pt_width_and_is_enabled`
asserts `rect.right() <= 650.0` — the earlier "wrong tool" the finding above
names) and windowed-re-verified — §12.

### 8.3 The default `⌘,` never opens Preferences — `FAIL`

`ShortcutAction::OpenPreferencesWindow` defaults to `Ctrl+,` (`⌘,` on macOS)
and both the Help menu and the Shortcuts tab advertise `Cmd+Comma`, but
pressing it does nothing. Isolated with three experiments in one run:

1. `⌘O` (`OpenImportWindow`, consumed two lines away in the same
   `handle_global_shortcuts` block) **works** — it opened the native Open
   panel — so command-modified shortcuts do reach the app.
2. In Preferences → Shortcuts, with the `Open Preferences Window` row in its
   `Press shortcut…` capturing state, pressing `⌘,` left the field **still
   capturing** and wrote nothing `[38]`; pressing `⌘⇧K` immediately after was
   captured and persisted as
   `OPEN_PREFERENCES_WINDOW = "Ctrl+Shift+K"` `[39]`. So egui never sees a
   `Key::Comma` for that keystroke — the failure is at key delivery/mapping,
   not in `consume_shortcut`, and not in the Preferences-opening code.
3. Pressing the newly bound `⌘⇧K` **did** open the Preferences window,
   confirming both the global-shortcut path and live re-apply of a rebound
   shortcut.

Caveat recorded honestly: all keystrokes here are synthetic `CGEvent`s. Two
other synthetic shortcuts in the same session worked, which makes a
harness-only artefact unlikely but not impossible — a human should confirm
`⌘,` on a physical keyboard before the root cause is called. Impact if
confirmed: the documented default shortcut for the Preferences window is dead;
Help → Preferences… and any other binding work.

**Investigated further (Task 17), verdict: in-app handling is correct —
caveat stands, unresolved.** Four additional source-level checks, all
negative for an in-app bug:

1. `shortcuts.rs::parse_key`/`key_token` already map `","` ↔ `Key::Comma`
   correctly both ways, pre-existing unit-tested (`ctrl_comma_is_comma_key`).
2. `views/main_window.rs::handle_global_shortcuts`'s
   `input.consume_shortcut(&shortcuts.get(ShortcutAction::
   OpenPreferencesWindow))` line is unremarkable — the same shape as the
   `⌘O` line two above it that is confirmed working.
3. `views/prefs_shortcuts.rs::resolve_capture_event` (the Shortcuts-tab
   capture field's own handler) has no special-casing that would drop
   `Key::Comma` — it resolves through the same `shortcuts::key_token` table.
4. The vendored `egui-winit-0.35.0` source's own macOS key mapping is correct
   on **both** paths a real keystroke can take: the physical path
   (`key_from_key_code`: `KeyCode::Comma => Key::Comma`, `lib.rs:1524`) and
   the logical path (`key_from_winit_key`: `Key::Character(str) =>
   egui::Key::from_name(str.as_str())`, `lib.rs:1426`, and
   `egui::Key::from_name`'s own table matches `"," | "Comma" => Self::Comma`).
   `on_keyboard_input` prefers `logical_key.or(physical_key)` (`lib.rs:999`),
   so either path alone would suffice. Also checked and ruled out: winit's
   own default macOS app menu (`platform_impl/macos/menu.rs::initialize`,
   gated on `default_menu` and installed for every winit app) does **not**
   bind any `⌘,`/Preferences menu item — About/Hide/Hide Others/Show
   All/Quit only — so it cannot be intercepting the key equivalent before
   the event reaches the window.

A new end-to-end test,
`kittest_actions.rs::cmd_comma_opens_preferences_via_the_global_shortcut`,
injects a genuine `egui::Key::Comma` + `Modifiers::COMMAND` event through a
real `HummApp` harness (bypassing `CGEvent`/winit entirely) and asserts
Preferences opens. It **passes**, which proves the entire in-app path —
`parse_key` → `consume_shortcut` → `handle_global_shortcuts` →
`preferences_requested` harvest — is correct end to end once egui actually
receives a `Key::Comma`. Combined with (1)-(4) above, the failure is not
reachable anywhere in this codebase's own source; it has to be in the
CGEvent → macOS event translation → winit delivery pipeline for this
specific key + modifier combination, which no amount of further source
reading can confirm or rule out. **The physical-keyboard confirmation this
document originally deferred stays deferred** — this pass narrows *where*
the gap must be, it does not close it.
