# GUI manual checklist — v5 (M7: preferences, folder watch, native post-processing, locales, live-API)

Scope: every M7 surface (F-030, F-100, F-101, F-005 editor half, F-044 full,
F-008, F-061b, F-110/F-111/F-113/F-115/F-116 config) on top of the standing
v1–v4 checklists. Executed 2026-07-26, Apple M4 / macOS 26.5.2, release
binaries at `1201ef9`, sandbox-lifted, isolated `HUMM_DATA_DIR`/
`HUMM_CONFIG_DIR`/`HUMM_LOG_DIR` per run (`HUMM_MODEL_ROOT` left unset so runs
use the real cached models, exactly like a real launch).

**Disposition vocabulary** (one per item):

| Tag | Meaning |
|---|---|
| `RUN-automated` | Executed this pass against a real `humm-gui` process, in a real OS window, with the evidence quoted inline. |
| `RUN-manual-pointer-deferred` | Not executed; needs a human judgment or an interaction this pass could not safely make. Its automated (kittest/unit) analogue is cited. |
| `BLOCKED-env` | Cannot run in this environment at all; the blocker is named concretely. |

## 0. What changed about this environment (and what it does *not* excuse)

M3–M6 recorded "no Accessibility/Screen-Recording grants for the automation
shell" and deferred every pointer item on that basis. **That is no longer
true**: this pass verified that `screencapture` captures real windows, that
`CGWindowListCopyWindowInfo` enumerates `humm-gui`'s viewports (id, title,
origin, size), that macOS System Events can read humm's AccessKit tree
(`get name of every button of group 1 of window 1` returns the real toolbar
labels), and that synthetic `CGEvent` mouse/keyboard events reach the app.
So this milestone's windowed pass **drives the real UI with real clicks and
real keystrokes**, and a large block of the v1–v4 carried list is retired in
§11.

Three things this does *not* change:

1. **API keys are never typed into fields.** Standing policy: credentials do
   not get entered into forms by an automated pass. Every "type a key and
   click Test" item stays `RUN-manual-pointer-deferred` by choice, not by
   capability.
2. **Native OS dialogs are still off-limits** — file pickers, keychain
   password panels, permission prompts. Anything gated behind one stays
   deferred or blocked.
3. **Human judgment items stay human** — "does the meter look janky", "does
   the speed change sound right".

## 5. Folder watch runtime — real FSEvents, real window (F-030, §3.2–3.4)

This is the milestone's acceptance gate and the one item M7's task reviews
explicitly could not close: the integration suite
(`crates/humm-gui/tests/folder_watch_int.rs`) drives
`start_with_poll_watcher_for_test`, **not** the production
`FolderWatchService::start`, because FSEvents delivers zero events inside the
sandbox. Both runs below use the **production `start`** (i.e.
`notify::RecommendedWatcher` → macOS FSEvents) inside a real windowed
`humm-gui`, sandbox-lifted, driven only by settings — no test seam, no
feature flag, no env hook.

The design makes this a clean experiment: `run_worker` performs exactly one
initial scan and then blocks on its channel, rescanning **only** on a
`WorkerMsg::Fs` posted by the watcher callback. There is no timer and no
polling anywhere in the production path, so a file that appears after the
initial scan can only be noticed via a real FSEvents delivery.

    Settings: `enabled = true`, input/output dirs, `delete_processed_files =
    false`, `options.model_size = "tiny"`, `export_formats = ["txt","srt"]`.
    App launched 08:56:08 (initial scan sees an empty directory);
    `whisper-latvian.wav` copied in at 08:56:12. Result: `watch-out/` gained
    `whisper-latvian (transcribed on 26-Jul-2026 08-56-13).txt` and `.srt`

48. **A real live-API session (GUI, real HTTP, real server).**
    `BLOCKED-env`. humm-gui resolves the transcription key **only** from the
    OS keyring (`KeyringSecretStore`, service `humm`, entry `OpenAI API key`
    — there is deliberately no env override, `HUMM_SURFACE` §6). Both ways of
    getting a key into that entry from outside the app fail in a headless
    pass:
    - seeded with `security add-generic-password … -A`, the unsigned dev
      binary's first read raises macOS's **login-keychain password panel**
      ("humm-gui wants to access key "humm" in your keychain") and the
      process blocks indefinitely inside the read — the app's log stops
      dead on `keyring_core:262 — get password from entry Cred { domain:
      User, service: "humm", account: "OpenAI API key" }`. Answering it
      needs the user's login password, which an automated pass must not
      enter.
    - seeded with an explicit trusted-app ACL (`-T <binary>`), the read
      instead **fails closed** — the warning quoted in item 47 — because an
      ad-hoc-signed dev binary does not satisfy the stored requirement.

    Both outcomes are environment facts, not humm defects (a signed,
    installed app bundle owns its own keychain items and neither prompts nor
    fails). What this blocks is only the *GUI half*; the wire behavior is
    covered below.
49. **`task = Translate` must post to `/audio/translations`, not
    `/audio/transcriptions`** (ledger #L15's closure, the one link Task 18's
    own report flagged as uncovered end-to-end). `RUN-automated` **against a
    real server**, through the CLI arm of the identical rule
    (`engine.rs:121-124`, which Task 18 ported verbatim into
    `LiveApiTranscriber::transcribe_chunk`): a stock Homebrew whisper.cpp
    `whisper-server` (ggml-tiny) behind `validation/m6-real-api/oai_shim.py`
    with the new `--request-log`, driven by
    `humm add … -m openaiapi -t transcribe|translate`. The shim's request
    log records exactly:

    ```
       1 POST /v1/audio/transcriptions
       1 POST /v1/audio/translations
    ```

    and the two calls produced **different** text from the same input, as the
    two endpoints should: the transcriptions call kept the source-language

## 10. Findings from this pass (new — not previously recorded)

### 10.1 No CJK-capable font is bundled (affects F-008's CJK locales)

`humm-gui` ships egui's default font set and never calls
`ctx.set_fonts`/`FontDefinitions` (verified: zero matches for
`FontDefinitions|font_data|set_fonts` across `crates/humm-gui/src`). Every CJK
codepoint therefore renders as `□`. Two visible consequences today:

- the whole `zh_CN` UI (item 54);
- **even under `en_US`**, the Post-processing tab's default punctuation
  string (`AutoResizeSettings::DEFAULT_PUNCTUATION`,
  `crates/humm-core/src/settings.rs:504`) renders
  `.* /./. /□/?/? /□/!/! /□/,/, ` — the constant carries **three** non-ASCII
  marks, not one (Buzz's CJK full stop `。`, fullwidth question mark `？`, and
  fullwidth exclamation mark `！`), and all three are missing glyphs. Three
  tofu boxes, not one. Functionally harmless (the string is correct in
  `settings.toml` and correct at split time) but visibly broken in the field
  the user is meant to edit.

This is a shipping-quality gap for F-008, not a porting error: Buzz gets CJK
for free from Qt's system-font fallback; egui has no fallback and needs an
embedded face. Recommended M8 ticket: bundle a CJK-capable font (or load a
platform face) and register it in `FontDefinitions` — one function, no
architectural change. F-008's matrix row is currently `in-progress`
(`docs/analysis/PARITY_MATRIX.md:22`), not `implemented`; the `in-progress →
implemented` flip is owned by the §12 milestone sweep (Task 21), and that
sweep must weigh this CJK tofu finding when making it — it must be recorded
before any CJK locale is called done.

### 10.2 The six-tab strip overflows the 650 pt minimum width at large fonts

With `ui.font_size = 24`, the Preferences tab strip needs more than the
window's 650 pt minimum width: `Post-processing` is clipped at the right edge
and `Privacy` is off-screen entirely, with no wrap and no scroll. The window
is resizable, so a user can widen it and recover — but at the documented
maximum (32) the strip is unreachable at minimum width. Candidate M8 fix:
wrap the strip, or scale `min_inner_size` with the font scale. Not a
regression (the tab strip only reached six entries in M7) and not blocking.

### 10.3 The live smoke hook needs a pumped UI thread

One live-fixture run (the first attempt at §"live ratio" pair 3, see
`docs/benchmarks/M7.md` §4.2's harness note) ran 11.5 minutes past its 200 s
window because
`apply_smoke_live_fixture_tick` never fired the Stop: the hook is a UI-frame
tick, and the frames stopped while the window sat fully occluded and the
machine idle. The session thread itself kept working correctly the whole
time (state creations continued at the expected cadence) — this is a
*harness* hazard, not an app defect, but it invalidates a measurement
silently. Every subsequent windowed run in this pass runs under
`caffeinate -dimsu`, activates the app after launch, and carries a watchdog
that kills and flags an overrun. Recorded here so the next milestone's
acceptance run does not rediscover it.
