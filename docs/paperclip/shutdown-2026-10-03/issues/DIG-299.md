###### R2.5 — required: cancellation at spawn exit skips command finalization and releases the build lock before joining its child

**Paths:** `scripts/run_owned_rust_checks.py:220–251` (`spawn` mask restoration and `Supervisor.run`), `:490–497` (`run_commands`), `:584–600` (`build_binary`). Regression gap: `tests/unit/test_owned_rust_target.py:524–544` checks spawn ownership separately from command finalization.

`spawn()` safely registers its child, but restoring its signal mask at line 221 delivers a pending TERM and raises `Cancelled`. `run()` calls `spawn()` at line 231 **before** its try/finally starts at line 233. Therefore the registered child is left for the outer `supervised()` cleanup; the local command outcome and cleanup are never finalized. When the caller is `build_binary()`, its finally unlocks at line 600 before outer cleanup reaches that still-running child. The comment that `run()` has already joined the build is false on this path.

**Independent reproductions, using a real finite child and real TERM:**

1. Invoke `run_commands`, queue TERM immediately after `Popen` returns (while masked), then let `spawn()` restore its mask. The command row remains `outcome="starting"` with argv/cwd/log but **no** exit, final status or cleanup. The global cleanup later joins the child with exit `-15`.
2. Invoke `build_binary` under a scratch lock, substitute a finite Python sleeper for the would-be Cargo child, and queue the same TERM. At the first outer `stop()` call, that child is in `/proc` state **R**, and a separate file descriptor successfully acquires the supposedly held build lock. Global cleanup subsequently joins it. No actual Cargo process, database, or network was used in this probe.

**Invariants first / Failure modes before happy path:** registration guarantees eventual ownership, but the caller also requires synchronous cleanup before unwinding its critical section. **Blast radius:** another task may enter the shared Cargo target while the first build still runs; the report also fails to describe the cancelled command's result. Eventual successful global cleanup does not satisfy either invariant.

**Concrete fix:** extend the command's guarded lifetime to include creation/registration and cancellation delivery. Give `run()` a reliable reference to the registered `Owned` entry even if spawning raises (for example, register into a call-owned holder before unmasking). Its finally must stop/join that entry, update the already-persisted row to `cancelled` with final status and cleanup, and only then propagate cancellation to `build_binary`. Handle the no-child/start-failed case explicitly. Do not depend on outer `supervised()` to satisfy the build lock's lifetime. Persist the build outcome before starting it as well.

Add real boundary regressions that call **both `run_commands()` and `build_binary()`**, not only `spawn()`: queue TERM after Popen and during identity capture; require `outcome=cancelled`, complete per-command cleanup/final status, all children joined, and a competing lock acquisition to remain blocked until that join.
