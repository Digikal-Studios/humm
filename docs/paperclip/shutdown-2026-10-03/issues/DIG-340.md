This task waits for that accepted target so project pointers resolve reliably. Preserve existing source/recovery gates; no product implementation.

##### Required project guidance

For each repo, inspect its README and existing agent/contributor entrypoints, current default branch and workflows. Add a short human-visible KB link and useful agent guidance in the appropriate existing file (root AGENTS.md where used; otherwise the repository’s actual instruction entrypoint). Preserve all existing instructions and local overrides. Avoid unrelated restructures or generic policy replacement.

Each project must have a working link to the canonical KB index, its exact `knowledge/projects/<slug>/README.md` page and relevant contribution/convention guide. Explain how to clone/find the KB, consult project architecture/status/decisions and applicable domain guidance before work, check sources and freshness/confidence, and propose a sourced update after decisions or discoveries. Repository-local instructions and verified source retain their scope; KB pages do not automatically override them. Include guidance for inaccessible private KB access without embedding credentials. Do not require a host-local absolute path.

##### Delivery and evidence

Use small documentation-only commits/PRs, retaining branch provenance. All changes require the usual independent review and approved landing path. Do not merge a change that unexpectedly publishes images/packages or deploys services; obtain a technical route through DevGuru that preserves the release gate. User authorization here covers KB/documentation population and repo pointers, not deployments. Application builds are unnecessary unless a specific docs workflow requires them.

Save a `project-adoption` document with an 18-row matrix: repository, default ref, changed entrypoint paths, resolved KB project-page URL, PR, accepted commit/merge SHA, default-branch remote verification and fresh-clone navigation check. Check all targets exist. Completion requires discoverability from normal default-branch clones for all 18 projects; pending PRs remain incomplete. The KB repo’s own README/contribution guidance is delivered by the migration task.

Coordinate final archive and source-inventory deltas through [DIG-337](DIG-337.md) and [DIG-338](DIG-338.md). This task does not depend on either; they capture its outputs. Do not modify credentials, clear held issues, enable timers, implement frozen tasks, or delete old KB snapshots.

##### How each column was checked

- **Default ref:** Forgejo `default_branch` and `git ls-remote --symref <repo> HEAD`, re-checked immediately before merging. Three default refs are not `main`: nurikabe (`codex/nurikabe-implementation`), zimam (`claude/resume-zimam-second-review-34a1a6`) and j-bot (`master`). DevGuru confirmed targeting them, since they are what a normal clone checks out.
- **Pre-merge gate:** each PR was open and mergeable, and its head equalled the approved SHA. Base = repository default. Actions was enabled only on RustView and nurikabe, and there were zero push mirrors and zero webhooks on all 18 repositories. All of this matches the reviewed state.
- **Accepted merge SHA:** the `merge_commit_sha` Forgejo returned. Each one equals the remote default-branch HEAD, and its second parent is the DevGuru-approved head.
- **Fresh-clone navigation:** each repository was cloned with a plain `git clone https://repo.digikal.com/jawad/<repo>.git`, with no `-b`, so the clone checks out the default branch. In that clone, every file changed by the merge has the `## Digikal knowledge base` heading. Each also links the exact `knowledge/projects/<slug>/README.md`, the KB index and `CONTRIBUTING.md`. Where a README points to a local agent file (`<FILE>.md#digikal-knowledge-base`), that file's heading exists. Every distinct KB URL in the changed files was fetched through the authenticated `raw/branch/main/…` route on KB `main` and returned HTTP 200. The `src/` web route needs a logged-in browser session for a private repository, so rendering in a browser was not checked.

##### Placement per repository

- An existing agent entrypoint gets the full guidance appended at the end, outside any `ai-engineering-governance` managed block. The README gets a short, human-visible block that points to it.
- **Only one agent file:** aletheia and tvi get the guidance in `AGENTS.md` only. Their docs set one home per rule: aletheia's `CLAUDE.md` names `AGENTS.md` as the tool-neutral entry, and tvi's `CLAUDE.md` § "Maintaining these docs" assigns conventions to `AGENTS.md`.
- **Both files:** browser-native-rts-poc and honcho get it in `AGENTS.md` and `CLAUDE.md`, because both repos already keep parallel copies.
